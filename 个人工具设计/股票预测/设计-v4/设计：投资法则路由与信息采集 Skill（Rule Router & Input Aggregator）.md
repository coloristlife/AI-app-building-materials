

## 一、先回答你的两个核心问题

**1. 一个 user query 对应多个 rules 的情况存在吗？**

**非常常见，而且是常态而非例外。** 因为这些法则本身在设计上就不是互斥的——它们分别覆盖"价格位置""量价关系""情绪状态""仓位管理""账户纪律"等不同维度，一个真实的交易场景天然会同时触碰多个维度。例如：

> "这只票之前在低位横盘了两周，昨天放量创了新低，我手里还有仓位，已经连续两笔止损了"

这一句话会同时触发：

- 法则四-B（低位横盘破低分批低吸/空头陷阱）
- 法则三-B（低位缩量新低左侧试仓）—— 注意这里是"放量"不是"缩量"，与法则三-B **冲突**，需要提示
- 法则八-B（连续两笔止损熔断暂停）

所以路由层**不能只返回一个最佳匹配**，必须支持"多命中"，并且要能识别命中规则之间的**信号冲突**（这点很重要，下面会设计冲突提示机制）。

**2. 是否应该把多个命中规则所需的 input 汇总后，一次性问用户？**

**应该，而且这是本 skill 设计的核心价值点之一。** 原因：

- 多条规则之间存在大量**重复输入**（比如"当前价格是否处于高位"在法则二、三-A、三-B、四-A、四-B、九中都出现），如果按规则逐条去问，用户会被同一个问题问 5 次。
- 应该先建一个**去重后的共享输入字典（Canonical Input Schema）**，把所有命中规则的 Required Inputs 映射到统一的字段上，合并后只问一次。
- 而且要遵循原始 Rule Contract 里已经定义好的 **Input Resolution Rule 优先级**（用户已提供 → 外部工具获取 → 计算得出 → 询问用户 → 标记UNKNOWN），即：能自动拿到的（MARKET_DATA/DERIVED/NEWS_DATA）不问用户，只把 USER_CONTEXT/USER_CONFIRMATION 类的缺失项汇总后**一次性、批量**地问。

## 二、Skill 整体架构

```
用户输入(自然语言描述市场情况)
        ↓
【模块一】情境标签抽取 (Situation Tagger)
        ↓
【模块二】规则匹配 (Rule Matcher) —— 支持多命中
        ↓
【模块三】输入需求聚合与去重 (Input Aggregator)
        ↓
【模块四】输入解析优先级执行 (Input Resolver)
     ├─ 已在query中提供 → 直接采用
     ├─ MARKET_DATA/DERIVED/NEWS_DATA → 调用工具自动获取
     └─ USER_CONTEXT/USER_CONFIRMATION 且缺失 → 汇总进"待询问清单"
        ↓
【模块五】一次性批量询问用户 (Batched Elicitation)
        ↓
【模块六】多规则并行评估 (Multi-Rule Evaluation)
        ↓
【模块七】冲突检测与综合输出 (Conflict Detection & Synthesis)
```

---

## 三、模块一：情境标签抽取（Situation Tagger）

给每条规则的 Applicability 条件抽象成标准化标签，query 进来后先打标签，再去匹配规则，而不是直接做语义相似度匹配整段规则文本（更精确、更可控）。

标签体系示例（维度 → 取值）：

|维度|取值示例|
|---|---|
|价格位置|高位 / 低位 / 中位 / 未知|
|成交量|放量 / 缩量 / 平量|
|价格速度|急跌 / 缓跌 / 急涨 / 平稳|
|形态|横盘 / 三连阴 / 十字星/三星 / 新低 / 新高 / 破位 / 回踩|
|时段|早盘 / 尾盘 / 盘中|
|情绪|恐慌 / 贪婪 / 人声鼎沸 / 中性|
|消息面|利好公告 / 利空 / 无消息|
|均线状态|年线走平 / 年线向下 / 年线拐头向上|
|标的属性|热门题材股 / 非题材股|
|账户/仓位状态|已止损 / 连续止损 / 有浮盈 / 浮盈回吐 / 已解套 / 已止盈后卖飞|

**执行方式**：对用户 query 做关键词/语义抽取，凡是命中上表任一取值，就打上对应标签。同一句话可以同时命中多个维度的标签（这正是"一 query 多 rule"的根源）。

## 四、模块二：规则匹配表（Rule Matcher）

把之前设计的每条规则的 Applicability 用标签固化成一张**规则索引表**，路由时做标签交集匹配，命中越多相关标签，置信度越高。

|规则ID|规则名|触发标签（AND关系为主，部分OR）|
|---|---|---|
|R1|逆向乖离法则|时段(早盘/尾盘) + 形态(急跌/急涨)|
|R2|趋势锚定法则|均线状态(年线走平/向下/向上) + [形态:回踩]可选|
|R3-A|高位放量下跌减仓|价格位置:高位 + 成交量:放量 + 价格速度:下跌|
|R3-B|低位缩量新低试仓|价格位置:低位 + 成交量:缩量 + 形态:新低|
|R3-C|增量回升右侧确认|形态:放量上涨(前) + 形态:次日回踩不破|
|R4-A|高位横盘冲高止盈|价格位置:高位 + 形态:横盘(前) + 形态:冲高|
|R4-B|低位横盘破低低吸|价格位置:低位 + 形态:横盘(前) + 形态:新低|
|R5-A|三连阴禁止抄底|阶段:下跌初期 + 形态:三连阴|
|R5-B|三星中继观望|阶段:下跌途中 + 形态:十字星×3|
|R6-A|缩量缓跌做T|价格速度:缓跌 + 成交量:缩量|
|R6-B|放量急跌低吸|价格速度:急跌/加速 + 成交量:放量|
|R7-A|利好兑现放量滞涨清仓|消息面:利好公告 或 情绪:人声鼎沸 + 成交量:放量 + 价格:滞涨|
|R7-B|热门题材股短线套利|标的属性:热门题材股|
|R8-A|等仓出击|场景:新建仓 (几乎每次建仓都可触发检查)|
|R8-B|连续止损熔断|账户状态:连续两笔止损|
|R8-C|止损铁律|形态:破位 或 板块:退潮 或 账户状态:亏损达2%|
|R9|贪婪恐惧法则|情绪:贪婪/恐惧(市场整体)|
|R10|本金保护法则|账户状态:有浮盈+浮盈回吐+逼近本金|
|R11|卖飞情绪法则|账户状态:已解套/已止盈后 + 价格:继续上涨|
|R12|位置反向评判法则|价格位置:高位+存在故事 或 价格位置:低位+业绩不佳|
|R13|显而易见法则|（无可操作化触发标签，仅作为兜底的思维提醒，见下方说明）|

**匹配输出**：不是选一个 Top-1，而是返回**所有标签交集非空的规则**，按命中标签数量排序，形成一个"候选规则列表"，每条附带命中置信度（如 "3/3 条件全部命中" vs "2/3 部分命中，建议向用户确认剩余条件"）。

## 五、模块三：共享输入字典（Canonical Input Schema）——去重的关键

这是避免"重复提问"的核心设计。把所有规则里出现过的 Required Inputs，归并成一份唯一的字段字典，每个字段只定义一次：

|字段ID|字段名称|类型|默认来源(Evidence Source)|被哪些规则引用|
|---|---|---|---|---|
|`price_position`|当前价格所处位置(高位/低位/中位)|衍生数据|DERIVED|R2,R3-A,R3-B,R4-A,R4-B,R12|
|`volume_state`|当前成交量相对均量状态(放量/缩量/平量)|市场数据+衍生|MARKET_DATA→DERIVED|R3-A,R3-B,R3-C,R6-A,R6-B,R7-A|
|`price_speed`|价格变动速度(急跌/缓跌/急涨)|衍生数据|DERIVED|R1,R6-A,R6-B|
|`is_consolidation`|此前是否横盘及横盘区间|衍生数据|DERIVED|R4-A,R4-B|
|`candle_pattern`|近期K线形态(三连阴/十字星/阴阳线)|市场数据|MARKET_DATA|R1,R5-A,R5-B|
|`ma250_trend`|年线(250MA)形态及斜率|衍生数据|DERIVED|R2|
|`current_position`|当前是否持仓/持仓比例|用户上下文|USER_PROVIDED/USER_CONFIRMATION|R3-A,R3-C,R8-A,R8-C,R10 几乎全部动作类规则|
|`entry_cost`|买入成本/本金|用户上下文|USER_PROVIDED|R8-C,R10|
|`max_floating_profit`|曾达到的最高浮盈|用户上下文|USER_PROVIDED/USER_CONFIRMATION|R10|
|`recent_trade_results`|最近交易结果(止损/止盈序列)|用户上下文|USER_PROVIDED/USER_CONFIRMATION|R8-B|
|`total_capital`|总资金规模|用户上下文|USER_PROVIDED|R8-A,R8-C|
|`original_thesis`|原始买入逻辑|用户上下文|USER_PROVIDED|R8-C|
|`sector_state`|板块/题材是否退潮|新闻/用户上下文|NEWS_DATA/USER_CONFIRMATION|R8-C,R7-B|
|`is_hot_theme_stock`|是否为热门题材股|用户上下文/新闻|USER_CONFIRMATION/NEWS_DATA|R7-B|
|`has_good_news`|是否存在利好公告|新闻数据|NEWS_DATA|R7-A|
|`market_sentiment`|市场/标的情绪状态(贪婪/恐惧)|用户上下文/新闻|USER_CONFIRMATION/NEWS_DATA|R1,R7-A,R9|
|`sell_reason`|该笔交易卖出原因(解套/止盈/止损)|用户上下文|USER_PROVIDED|R11|

**关键规则**：路由匹配出候选规则列表后，把这些规则各自的 Required Inputs 映射到上表字段ID，做**并集去重**，得到这次交互真正需要的最小字段集合，而不是把每条规则的输入表单独罗列。

## 六、模块四+五：输入解析优先级 + 一次性批量提问

严格复用你最初 Rule Contract 里定义的 **Input Resolution Rule** 优先级，按顺序过一遍去重后的字段集合：

```text
对去重后的每个字段：
1. 检查用户原始 query 中是否已包含 → 已提供，跳过
2. 若来源标注为 MARKET_DATA/NEWS_DATA/DERIVED → 尝试调用行情/新闻/计算工具自动获取
3. 若获取失败或来源为 USER_CONTEXT/USER_CONFIRMATION → 加入"待询问清单"
4. 若某字段对某条候选规则是"非必要"输入(如R2中的具体回踩幅度) → 允许标记UNKNOWN不强制询问
5. 若某字段是判断该规则"是否触发"的必要条件(如R8-C的total_capital用于算2%止损线) → 标记为必须询问
```

最终"待询问清单"里的字段，**合并成一轮问题**一次性发给用户，而不是按规则分批问。例如上面举的例子（低位横盘破新低+连续止损）汇总后大概是：

- 当前是否仍持有该仓位？占多少仓位比例？
- 最近两笔交易是否都是止损离场？
- 当前总资金规模大致是多少（用于计算止损上限）？

而"价格是否处于低位""成交量是放量还是缩量""是否横盘"这些 MARKET_DATA/DERIVED 类字段，系统应该**先尝试自己查**，查不到才问，不要和上面几个用户专属信息混在一起一次性甩给用户一堆问题——这里可以做一个**优先级分层**：能自动拿到的先拿，实在拿不到、且是必要输入的，才进入"必须问用户"的那一轮。

## 七、模块六+七：多规则并行评估 + 冲突检测

拿到共享输入池后，**并行**跑每条候选规则各自的 Evaluation 逻辑（因为输入已经去重共享，一份数据可以喂给多条规则，不需要重复计算）。

输出时做**冲突检测**，这一步很重要，因为规则之间确实会互相矛盾（前面很多条法则的 Limitations/AI Interpretation 部分已经互相提到过这种冲突可能性）：

已知的潜在冲突对（应在 skill 里预先登记一张"冲突矩阵"）：

|规则A|规则B|冲突点|
|---|---|---|
|R3-B(低位缩量试仓)|R6-B(放量急跌低吸)|同为"低位/下跌"场景，但一个要求缩量、一个要求放量，两者互斥，query若模糊描述"跌得厉害"需先确认量能|
|R5-A(三连阴禁抄底)|R3-B/R6-B(试仓/低吸)|都可能出现在下跌阶段，但动作相反(严禁 vs 可以)，取决于是否处于"下跌初期"还是"低位/恐慌尾声"|
|R2(熊市只做超跌反弹)|R4-B(低位破位低吸/黄金坑)|熊市格局下的"破位"到底是继续探底还是黄金坑，两条规则给出的仓位重量不同，需要综合年线状态|
|R3-A(高位放量下跌减仓)|R6-B(放量急跌低吸)|若高位放量急跌同时满足两者的表面条件，需要看是"高位派发"还是"恐慌抛售"，性质不同|

**输出格式设计**：不是简单罗列每条规则的结论，而是：

```markdown
## 本次命中的规则（按相关度排序）

1. [R3-B 低位缩量新低试仓] — 状态：TRIGGERED
2. [R8-B 连续止损熔断] — 状态：TRIGGERED
3. [R4-B 低位横盘破低低吸] — 状态：INCONCLUSIVE（横盘持续时间信息不足）

## ⚠️ 检测到规则间的潜在张力
R3-B 建议左侧小仓位试仓，但 R8-B 显示你已连续两笔止损，
按纪律应先暂停交易、调整心态，而非立即执行试仓动作。
建议：优先遵守 R8-B 的熔断纪律，暂缓本次操作。

## 各规则详细依据
[展开每条规则的 Evidence / Missing Inputs / Limitations]
```

即：**当纪律类规则（法则八系列）与信号类规则同时触发时，默认给纪律类规则更高优先级提示**，因为账户风控纪律的性质决定了它应该"一票否决"信号类规则的执行建议——这条优先级关系本身也应该显式写进 skill 的设计文档里，而不是留给模型临时决定。

## 八、关于 R13（显而易见法则）的特殊处理

前面已经指出，这条经验没有可操作化的触发标签，路由层应该**永远不主动匹配**这条规则去参与"触发判断"，只在用户明确要求"帮我review一下这个机会是否被低估"这类**元认知复盘**场景下，作为一种引导性提问模板单独调用，不进入常规的多规则并行评估流程。

## 九、这个 Skill 的最小可执行流程（伪代码总览）

```text
function route_and_evaluate(user_query):
    tags = extract_situation_tags(user_query)
    candidate_rules = match_rules(tags)  # 可能返回0~N条

    if len(candidate_rules) == 0:
        return "未匹配到明确规则，可能需要更具体描述市场情境"

    required_fields = union([rule.required_inputs for rule in candidate_rules])
    # 按 canonical schema 去重

    resolved, missing = resolve_inputs(required_fields, user_query, tools=[market_data, news])
    # 优先级：query已有 > 工具自动获取 > 标记缺失

    if missing (且为必要字段):
        ask_user_once(missing)  # 一次性批量问，不分规则多次问
        return  # 等待用户下一轮回复

    results = [evaluate(rule, resolved) for rule in candidate_rules]
    conflicts = detect_conflicts(results, conflict_matrix)
    return synthesize_output(results, conflicts, priority=DISCIPLINE_RULES_FIRST)
```
