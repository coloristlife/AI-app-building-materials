# 投资法则路由器

本技能让用户的个人投资法则库（每条法则遵循七段式法则契约：目的 / 适用范围 / 必需输入 /证据来源 / 评估逻辑 / 输出 / 局限性）真正在对话中"用起来"：给定一段用自然语言描述的市场情况，
本技能会找出所有可能适用的法则，梳理清楚评估这些法则还缺哪些信息，把这些缺失信息**合并成一轮
问题一次性**向用户询问，然后统一评估——并在两条匹配法则给出相互矛盾的建议时，明确指出这种矛盾。

用于日常路由匹配、去重提问和快速评估的数据（标签词表、法则索引表、标准化输入字典、冲突矩阵、各法则精简评估逻辑）都保存在 `references/rule_library.md` 中。在进行任何匹配或评估
之前，必须先加载该文件——它是日常操作的事实来源，本文件不重复承载具体规则内容。

每条法则的**完整七段式契约原文**（完整的适用范围说明、每项输入的详细理由、AI补充解释、
待澄清问题等）分别保存在 `references/rules/` 目录下的独立文件中，`rule_library.md` 开头
有对照表列出每条法则对应的文件路径。**不要**在日常路由/评估时预先加载这些完整文件——只有
当用户明确要求查看某条法则的完整依据、要求修改/复核某条法则、或要新增法则需要参照契约格式
时，才按需读取对应的单个文件。

每次使用本技能后，都必须按 `references/log_schema.md` 定义的结构生成并保存一条决策日志
记录，用于后续人工审核和法则改进——见下方第八步。在开始第一步之前，先加载
`references/log_schema.md`，了解本次会话结束时需要收集哪些字段，这样才能在第一到第七步的
过程中随手记录下这些信息，而不是等到最后才发现漏了什么。

## 核心原则：一个用户问题常常、也理应匹配多条法则

不要试图寻找"唯一最佳"的一条法则。真实的交易情境几乎总是同时落在多个维度的交叉点上
（价格位置、成交量、市场情绪、账户纪律状态），而这套法则库本身在设计上就是"一个维度一条法则"，
而非"一条大而全的规则"。请把"这次到底命中了几条法则"当作每次都需要根据实际情况重新判断的
开放问题，而不是刻意去压缩命中数量。

## 核心原则：宁可说未知，绝不编造

任何一个情境标签、任何一项必需输入，只要没有真实的检索结果或用户的明确陈述作为依据，就必须
标注为"未知"，绝不允许基于经验概率、常见走势模式或"大概率是这样"的直觉去填入一个具体结论
（例如凭感觉断定"这类票放量下跌通常是高位"）。宁可让候选法则的状态停留在 INCONCLUSIVE 或
INSUFFICIENT_DATA，也不要用编造的判断把某条法则强行推成 TRIGGERED 或 NOT_TRIGGERED。
每一次给出"已核实"的标签或字段时，都应能说出具体的依据来源（搜索到的哪条数据、用户的哪句话），
说不出依据来源的，一律改记为"未知"。

## 工作流程

每次触发本技能时，按以下步骤依次执行。不要跳过第五步的"合并提问"环节——这是本技能存在的
核心意义；如果用五种不同法则的措辞把同一个底层问题反复问用户五遍，就是本技能要避免的失败模式。

### 第一步 —— 先联网核实，再提取情境标签

在给用户消息打标签之前，**先尝试通过网络搜索/行情数据工具，把能够客观核实的情境标签补全**，
而不是仅凭用户的文字描述或自己的记忆去猜测，严格匹配情境标签，不要自己再创造新的情境标签。具体来说：

1. 先判断用户消息中是否包含了可识别的标的名称/代码。如果有，针对"情境标签词表"中**证据
   来源为市场数据/新闻数据/衍生计算**的维度（价格位置、成交量、价格速度、K线形态、横盘状态、
   年线走势、是否有利好/利空消息等），主动检索最新的行情数据和相关新闻，尝试逐项核实。
   **其中年线（MA250）走势的判断方式如下**：主要通过**约一年周期的K线图截图**（用户上传的
   图片，或通过工具检索到的行情图表截图）用视觉方式判断年线方向，具体做法：
   - 找到/获取一张覆盖约一年（约250个交易日）区间的K线图（图上应能看到年线/MA250这条
     均线，若图上没有画出该均线则无法判断，记为未知）；
   - 目视判断该均线在图上呈现的方向：走平 / 向下 / 拐头向上；
   - 记录下这张图所覆盖的**具体起止日期区间**，以及**判断得出的结果**。
   在此基础上，**再尽量额外获取近30个交易日的MA250实际数值序列**作为对图片判断的校验
   （能拿到工具化的行情数据源时就去查，查不到就把这一项留空，不强行编造）；如果数值序列
   与图片目视判断的方向不一致，要在后续第八步的日志里标记出来，交给人工复核，不要自己选
   一个结论覆盖另一个。这些内容按 `references/log_schema.md` 中 `ma250_detail` 的结构
   记下来，留到第八步写入日志，同时把用于判断的那张图片本身也作为证据一并保存。
2. 如果用户消息中没有指明具体标的、只是描述一个抽象/假设情境，则跳过联网核实，直接进入
   下面的标签提取，市场数据类字段照常标注为未知。
3. 对于**证据来源为用户上下文/需用户确认**的维度（市场情绪是否人声鼎沸、是否为热门题材股、
   板块是否退潮、持仓/账户状态等），联网搜索可以作为辅助参考（例如查舆情热度、板块新闻），
   但最终判断仍需保留给用户确认，不能仅凭搜索结果替用户下结论。

**核实之后，必须先把每个维度的标签逐条列出来给用户看**，格式类似：

```text
已核实/已知：
- 价格位置：低位（近X日价格处于近Y个月区间低部）
- 成交量：放量（较5日均量放大约Z倍）
- 年线：走平

未知（无法通过公开数据核实，或用户消息未提及）：
- 是否横盘及持续时间：未知
- 是否存在利好/利空消息：未知
- 板块/题材是否退潮：未知
```

对每一个维度，只有两种合法状态：**"已核实"（附上依据来源）**或**"未知"**。严禁在没有
检索到实际支持依据的情况下，凭经验或概率把某个维度直接假定为某个取值——如果搜索没有结果、
没有找到相关标的、或标的信息本身模糊不清，一律如实标注为"未知"，绝不编造价格位置、成交量、
消息面等具体结论。

只有完成这一轮"联网核实+列出结果"之后，才能进入第二步的规则匹配；第二步匹配时，"未知"的
维度不参与命中判断，但会在第三步中作为需要向用户确认或补充的信息之一被重新拾起。

### 第二步 —— 匹配候选法则，并列出全部法则的匹配/不匹配结果及原因

阅读 `references/rule_library.md` 中的"法则索引表"。**必须逐一检查全部19条法则**（含所有
A/B/C子法则），而不是只挑看起来相关的几条来看。对每一条法则，把它的触发标签与第一步得到的
标签逐项比对，然后把结果**明确列出来**，分成两组：

**匹配的法则**：列出法则编号+名称，并说明具体是哪些标签命中了、命中程度如何（"完全匹配"——
该法则所有触发标签均已核实满足；或"部分匹配"——部分触发标签已满足，其余标签目前是"未知"，
需要在后续步骤中确认）。

**不匹配的法则**：列出法则编号+名称，并说明具体原因——是"触发标签与当前情境明确不符"（例如
该法则要求"高位"而当前已核实为"低位"），还是"相关维度目前未知、无法判断是否匹配"（例如
该法则需要"是否存在利好公告"这一标签，但第一步未能核实，暂时归为不匹配，但保留在后续澄清
清单中，一旦用户或后续搜索补上这项信息，可能需要重新纳入候选）。

输出格式示例：

```text
【匹配的法则】
- R3-B 低位缩量新低试仓：完全匹配（价格位置=低位、成交量=缩量、形态=新低 均已核实）
- R8-B 连续止损熔断暂停：部分匹配（用户提到"最近可能要止损"，但"是否已连续两笔"需要确认）

【不匹配的法则】
- R3-A 高位放量下跌减仓：不匹配，因当前已核实价格位置=低位，与该法则要求的"高位"相悖
- R7-A 利好兑现放量滞涨清仓：不匹配（未知），第一步未搜索到相关利好公告或情绪面信息，
  暂无法判断该法则是否适用
- R13 显而易见法则：不匹配，本法则不参与自动路由（无可操作标签），仅在用户明确要求
  元认知复盘时手动调用
- ...（其余法则同理逐条列出）
```

只有"部分匹配"和"完全匹配"的法则才进入第三步的候选列表参与后续的输入聚合与评估；"不匹配
（明确不符）"和"不匹配（未知）"的法则不再往下走，但都必须在这一步的输出中留痕，让用户能
看到完整的排查过程，而不是只看到最终挑出来的几条。

如果第一步产生的标签过少、导致几乎所有法则都落入"不匹配（未知）"，不要强行拼凑候选，而应
如实告知用户当前信息不足以做出判断，并说明还缺哪些关键信息。

**完成本步骤后，必须先把候选法则各自的完整"必需输入"清单列出来展示给用户**（不是等到
第三步去重合并之后才展示，而是先原样列出——每条候选法则各自需要哪些输入，参照
`references/rule_library.md` 各法则的 Required Inputs），格式例如：

```text
【本次匹配的法则各自所需的数据】
- R4-B 低位横盘破低低吸：需要 价格所处位置、横盘持续时间及区间、是否创新低、
  破低时成交量变化、可用资金/仓位空间
- R8-B 连续止损熔断暂停：需要 最近两笔交易结果、当前是否计划新交易
```

展示完这份清单后，才继续进入第三步（去重合并）以及后续步骤。这一步是为了让用户在AI继续
自动解析/提问之前，先看清楚"这次分析总共会涉及哪些数据"，不要跳过直接进入自动解析。

### 第三步 —— 汇总所需输入（去重）

在第二步已经把候选法则各自的完整必需输入清单展示给用户之后，接着做去重合并：阅读
`references/rule_library.md` 中的"标准化输入字典"。针对每一条候选法则，找出其"必需输入"，
并将每一项映射到该字典中统一的字段编号上。把所有候选法则的输入字段做**并集**——这个并集，
才是接下来第四、第五步实际要解析/询问的范围，而不是分别按每条法则各自的清单重复处理。

这一步正是为了避免重复提问：例如 `price_position`（价格位置）被约六条不同法则共用，但在
一轮对话里只应该被解析/询问一次。

### 第四步 —— 尽量自行解析，不要急于开口问

针对去重后并集中的每一个字段，按以下优先级顺序解析（这与法则契约本身定义的"输入解析优先级"
完全一致）：

1. **用户消息中已经明确提及，或已在第一步联网核实中得到确认** —— 直接采用，不再重复搜索
   或询问。
2. **证据来源 = 市场数据 / 新闻数据 / 衍生计算，且第一步未能核实** —— 再次尝试通过工具获取
   或计算；如果第一步已经明确标注为"未知"（说明已经搜索但确实查不到），不要在这一步凭空
   补一个猜测值，仍然保持未知，转入下一优先级。
3. **证据来源 = 用户上下文 / 需用户确认** —— 这类信息只能由用户提供（持仓比例、买入成本、
   总资金规模、最近交易结果、原始买入逻辑、主观情绪判断等）。这些字段进入第五步的合并提问。
4. 如果某个字段对于得出**任意**候选法则的规则状态并非必要，应直接标记为 UNKNOWN，而不是卡在
   这里不往下走——不要替用户制造他从未给出的精确度（"高位/低位"、"急跌/缓跌"等定性描述在
   用户未给出具体数字前应保持定性表述），也不要因为找不到数据就编一个看起来合理的数字。

### 第五步 —— 一次性合并提问

如果经过第四步仍有字段未解析，且这些字段对于得出至少一条候选法则的规则状态是必要的，应把
它们**合并成一轮**问题一起询问，按主题分组（持仓/账户信息归为一组，主观判断归为另一组），
而不是按法则逐条重复提问。当缺失字段可以归纳为少数几个离散选项时（例如"是否持仓？"是/否，
"止损结果"是/否），使用 `ask_user_input_v0`；当需要具体数字或自由文本回答时（例如买入成本、
总资金规模），使用普通的文字提问。同一批缺失信息**永远不要问第二轮**——如果用户的回答仍有
遗漏，应在最终输出中把它记为"缺失输入"，而不是再次追问。

在这一轮问题得到回答之前，不要进入第六步（提问后应结束当前回合，等待用户回复）。

### 第六步 —— 并行评估所有候选法则

在共享输入池已经尽可能完整之后，独立评估每条候选法则的 IF/AND/THEN 判断逻辑，针对每条法则
分别输出：规则状态（已触发/未触发/无法判断/数据不足）、解读、建议动作、证据、缺失输入。
使用 `references/rule_library.md` 中记录的每条法则的评估逻辑——不要从零重新推导，也不要在
措辞上偏离该文件中已经确立的表述。

### 第七步 —— 冲突检测与综合输出

阅读 `references/rule_library.md` 中的"冲突矩阵"。检查第六步中任意两条"已触发"的法则是否
出现在该矩阵中。如果出现，必须明确指出这一冲突，而不是把两条建议动作原样并列展示——如果用户
看到"试仓"和"暂停交易"两条建议紧挨着出现却没有任何说明，将无法判断该听哪一条。

**当冲突涉及账户纪律类法则（法则八系列：仓位纪律 / 连续止损熔断 / 止损铁律）与信号类法则
（基于价格/成交量/形态的法则）时，默认将纪律类法则的建议动作作为应优先遵循的一条**，并将
信号类法则的结论降级为"背景信息"而非"立即执行的指令"。这与原始素材本身的设计意图一致——
纪律类法则存在的意义，正是为了在关键时刻凌驾于当下的信号判断之上。

对于不涉及纪律类法则的其他冲突，不要替用户做出最终选择，而应把两种解读并列展示，并给出能够
决定"到底该听哪一条"的具体判断条件（例如："如果这是下跌初期 → 法则五-A 更适用；如果这是
恐慌尾声的急跌 → 法则六-B 更适用——你觉得目前更接近哪种情况？"）。

最终答案应按以下结构呈现：
1. 第二步产出的"匹配的法则 / 不匹配的法则"完整清单（连同各自原因），置于最前面，让用户看到
   完整的排查过程。
2. 一句话的直接结论。
3. 命中了哪几条法则及各自的建议动作。
4. 冲突/优先级提示（如有）。
5. 各法则的证据和缺失输入，保持简洁——除非用户主动要求，否则不要把完整的七段式法则契约
   原文再复述一遍。

### 第八步 —— 记录与保存决策日志

阅读 `references/log_schema.md`，按其中定义的 JSON 结构，把本次会话第一步到第七步产生的
全部信息整理成一条完整的日志记录。这一步是强制的，不因用户没有主动要求"保存记录"而省略——
除非用户明确说"这次不用保存"。

执行顺序：
1. 检查 `/mnt/user-data/uploads/` 下是否存在用户重新上传的 `decision_log.jsonl`。若存在，
   读取其内容；若不存在，视为空列表。
2. 按 `log_schema.md` 的结构生成本次的新记录，`log_id` 用本次的时间戳生成，确保不与已有
   记录重复。
3. 将新记录追加到已有记录之后，写入 `/mnt/user-data/outputs/decision_log.jsonl`（JSON
   Lines 格式，一行一条）。
4. 同步生成/更新人类可读的 `decision_log_summary.md`（若已有旧文件则在其基础上追加新的
   小节），格式见 `log_schema.md` 第四节。
5. 用 `present_files` 把这两个文件呈现给用户，并提醒："请保留这两个文件；下次继续使用本
   技能时，重新上传 `decision_log.jsonl`（放入上传区）即可在其基础上继续累积记录，否则
   本次会话结束后这些记录不会自动留存到下一次对话中"。

`log_schema.md` 中要求的字段必须如实填写，尤其是：
- `situation_tags` 覆盖全部维度（已核实/未知都要列出），不能只记录已核实的部分
- `ma250_detail` 在涉及年线判断时，必须包含**判断所依据的K线图覆盖的起止日期区间**、
  **判断结果（走平/向下/拐头向上）**、**所用图片的来源说明**（用户上传的截图，还是工具
  检索到的行情图表），并**尽量附上近30个交易日的MA250数值序列**作为校验（拿不到时可以
  为空数组，但不能为了省事而不去尝试获取）
- `unmatched_rules` 覆盖第二步中判定不匹配的全部法则
- 任何"未知"字段却仍被某条法则判定为触发/不触发的情况，都要写入 `flags_for_human_review`

## 处理"新增法则"的请求

如果用户描述了一段全新的经验、希望将其转化为一条新法则（而不是与现有法则库做匹配路由），
这属于本文件顶部 `references/rule_library.md` 中"规则提炼原始说明"部分所描述的独立任务——
按照该契约完成提炼后，把生成的法则追加进"法则索引表"和"标准化输入字典"，以便未来的路由能够
找到它。在把新法则正式纳入可路由的法则库之前，先与用户确认。

## 本技能不适用的场景

- 法则十三（显而易见法则）以及其他任何"无法操作化的元原则"类法则，都**不应**在第二步中被
  自动纳入候选列表——它们没有可匹配的情境标签。只有当用户明确要求对某个机会做反思性/元认知
  层面的检视时，才手动调用这类法则。
- 本技能不能替代用户自身的风险判断——最终输出应保留触发法则各自的"局限性"说明，不应把结论
  当作确定性的事实呈现。
