## 一、 从真实的专业经验出发

在创建技能时，一个常见的陷阱是：在没有提供特定领域上下文的情况下，直接要求大语言模型（LLM）生成一项技能，这完全依赖于LLM通用训练集中的知识。这种做法的结果往往是生成含糊其辞、通用的操作步骤（例如：“恰当地处理错误”、“遵循身份验证的最佳实践”），而不是那些真正能让技能产生价值的特定API调用模式、边缘情况以及项目约定。

高效的技能应当植根于真实的专业经验。其中的关键，在于将特定领域的上下文信息注入到技能的创建过程中。

### 1. 从实际的动手操作任务中提取

你可以通过与Agent的对话来完成一项实际任务，在此过程中不断提供上下文、纠正错误以及表达你的偏好。任务完成后，再将这些可复用的模式提取成一项技能。在这个过程中，请密切关注以下几点：

* **行之有效的步骤** ：最终导向成功的具体操作序列。
* **你所做的纠正**：你引导Agent改变方法的具体节点（例如：“使用库X而不是库Y”、“检查边缘情况Z”）。
* **输入/输出格式** ： 数据输入时和输出时的具体形态。
* **你提供的上下文** ： Agent原本不知道的特定于该项目的事实、约定或约束条件。

### 2. 从现有的项目产物中提炼

当你拥有一套现成的知识体系时，你可以将其提供给LLM，并要求它提炼出一项技能。相比于根据通用的“数据工程最佳实践”文章生成的技能，由你团队实际的故障报告和运行手册提炼出的数据管道（data-pipeline）技能，其表现会优异得多，因为它捕获了**你们专属**的数据模式（schemas）、故障模式以及恢复流程。关键点在于：要使用项目专属的素材，而不是通用的参考资料。

优秀的源素材包括：

* 内部文档、运行操作手册以及代码风格指南
* API规范、数据模式（schemas）以及配置文件
* 代码审查评论和问题追踪记录（这类内容捕获了反复出现的问题以及审查者的期望）
* 版本控制历史记录，尤其是补丁和修复记录（通过实际修改的内容揭示了代码模式）
* 真实世界中的故障案例及其解决过程

## 二、 通过实际执行进行优化

技能的初稿通常都需要经过优化。你需要将技能应用于实际任务中进行测试，然后将结果（包括成功和失败的所有结果）反馈到创建过程中。你应该思考：是什么触发了误报？遗漏了什么？有哪些内容是可以删除的？

哪怕只进行一次“执行-修改”的循环，也能显著提升技能的质量；而复杂的领域通常需要经过多次这样的循环才能达到理想状态。

> 💡 **提示：**
> 不仅要看最终的输出，还要阅读Agent的执行轨迹（execution traces）。如果Agent在无益的步骤上浪费时间，常见的原因包括：指令过于模糊（Agent在找到有效方法前会尝试多种途径）、指令不适用于当前任务（但Agent依然照做），或者在没有明确默认选项的情况下给出了过多选择。

关于包含测试用例、断言（assertions）和评分的更结构化的迭代方法，请参阅“评估技能输出质量”相关文档。

## 三、 明智地使用上下文空间

一旦某项技能被激活，它完整的 `SKILL.md` 内容就会和对话历史、系统上下文以及其他激活的技能一起，加载到Agent的上下文窗口中。你技能中的每一个Token，都在与该窗口中的其他所有内容争夺Agent的注意力。

### 1. 补充Agent缺失的知识，省略它已知的常识

请将重点放在Agent在没有你的技能时**无法知道**的信息上：项目专属的约定、特定领域的流程、非显而易见的边缘情况，以及需要使用的特定工具或API。你完全不需要向它解释什么是PDF、HTTP是如何工作的，或者数据库迁移的作用是什么。

```markdown
<!-- 过于啰嗦 —— Agent 已经知道什么是 PDF -->
## 提取 PDF 文本

PDF（便携式文档格式）是一种常见的文件格式，包含文本、图像和其他内容。要从 PDF 中提取文本，你需要使用一个库。推荐使用 pdfplumber，因为它能很好地处理大多数情况。

<!-- 更好的做法 —— 直奔主题，直接提供 Agent 靠自己无法知道的信息 -->
## 提取 PDF 文本

使用 pdfplumber 进行文本提取。对于扫描版文档，请退而求其次使用带有 pytesseract 的 pdf2image。

import pdfplumber

with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```

对技能中的每一段内容，你都要问自己：“如果没有这条指令，Agent会做错吗？”如果答案是否定的，就删掉它。如果你不确定，那就去测试一下。如果Agent在没有该技能的情况下就已经能很好地处理整个任务，那么这项技能可能并没有提供额外的价值。

### 2. 设计连贯的工作单元

决定一项技能应该包含哪些内容，就像决定一个函数应该做什么一样：你希望它封装一个连贯的工作单元，并且能与其他技能良好地组合。如果技能的作用域太窄，就会导致处理一个任务时需要加载多个技能，增加了系统开销和指令冲突的风险；如果作用域太广，又很难被精准激活。举个例子，一个用于查询数据库并格式化结果的技能可能是一个连贯的单元，但如果这个技能还包含了数据库管理的功能，那它要做的就太多了。

### 3. 保持适度的细节

过于详尽的技能可能会适得其反，Agent会难以提取相关信息，并且可能会因为执行了不适用于当前任务的指令而走弯路。简明扼要、分步骤的指导加上有效的代码示例，往往比事无巨细的详尽文档表现得更好。当你发现自己在试图涵盖所有的边缘情况时，请考虑一下：大多数边缘情况是不是交给Agent自己来判断会更好。

### 4. 使用渐进式披露来构建大型技能

规范建议将 `SKILL.md` 保持在500行和5,000个Token以内，这是Agent在每次运行时所需的核心指令。当某项技能确实需要更多内容时，请将详细的参考资料移至 `references/` 或类似目录下的独立文件中。

这里的关键在于，要明确告诉Agent**什么时候**去加载这些文件。“如果API返回非200状态码，请阅读 `references/api-errors.md`” 要比通用的 “详情请参阅 references/” 有用得多。这使得Agent能够按需加载上下文，而不是在一开始全部加载，这也正是“渐进式披露（progressive disclosure）”的设计初衷。

## 四、 精准把控控制度

技能中的各个部分并不都需要同等程度的规范性。你需要根据任务的脆弱程度（fragility），来匹配指令的具体程度。

### 1. 将具体程度与脆弱程度相匹配

**当任务有多种有效的方法且允许一定差异时，请给予Agent自由。** 对于灵活的指令，解释“为什么”通常比死板的命令更有效，一个理解了指令背后意图的Agent，能做出更好的基于上下文的决策。比如，代码审查技能可以描述需要寻找什么，而不必规定确切的步骤：

```markdown
## 代码审查流程

1. 检查所有数据库查询是否存在 SQL 注入（使用参数化查询）
2. 验证每个端点（endpoint）上的身份验证检查
3. 在并发代码路径中寻找竞态条件
4. 确认错误信息没有泄露内部细节
```

**当操作十分脆弱、一致性至关重要或者必须遵循特定顺序时，请给出规定性指令：**

```markdown
## 数据库迁移

请严格按此顺序运行：

bash
python scripts/migrate.py --verify --backup


切勿修改此命令或添加额外的标志（flags）。
```

大多数技能都混合了这两种情况。你需要对每一部分进行独立校准。一个 Skill 里面既有应该“让 Agent 自己判断”的地方，也有必须“严格按照规定执行”的地方。不要用一种统一的控制强度覆盖整个 Skill，而是针对每个步骤分别决定自由度。

### 2. 提供默认选项，而不是菜单式选择

当有多种工具或方法可用时，请选择一个默认项，并简要提及替代方案，而不是将它们作为同等选项呈现出来。

```markdown
<!-- 选项过多 -->
你可以使用 pypdf、pdfplumber、PyMuPDF 或 pdf2image...

<!-- 提供明确的默认项和备用方案 -->
使用 pdfplumber 进行文本提取：

python
import pdfplumber


对于需要 OCR（光学字符识别）的扫描版 PDF，请改用带有 pytesseract 的 pdf2image。
```

### 3. 偏向“操作流程”而非“声明式结果”

一项技能应该教会Agent如何**处理一类问题**，而不是让它针对某个具体实例**生成特定内容**。请对比以下两例：

```markdown
<!-- 具体的答案 —— 仅对这一个确切的任务有用 -->
将 `orders` 表和 `customers` 表通过 `customer_id` 连接起来，筛选 `region = 'EMEA'` 的数据，并对 `amount` 列求和。

<!-- 可复用的方法 —— 适用于任何分析类查询 -->
1. 从 `references/schema.yaml` 读取数据模式（schema）以找到相关的数据表
2. 使用 `_id` 外键约定来连接数据表
3. 将用户请求中的任何过滤条件作为 WHERE 子句应用
4. 根据需要聚合数值列，并将结果格式化为 Markdown 表格
```

这并不意味着技能中不能包含具体细节，输出格式的模板（见下文）、诸如“绝对不要输出个人身份信息（PII）”的约束条件，以及针对特定工具的指令都是非常有价值的。核心观点是：即使个别细节是特定的，整体的**处理方法**也应该具备通用性。

## 五、 高效指令的设计模式

以下是用于构建技能内容的可复用技术模式。并非每一项技能都需要用到所有模式，请选择最适合你当前任务的模式。

### 1. 避坑指南（Gotchas）

在很多技能中，价值最高的内容就是“避坑指南”列表，那些颠覆常规假设、特定于环境的事实。这些不是泛泛的建议（如“恰当地处理错误”），而是针对Agent在没有被告知的情况下必定会犯的错误的具体纠正：

```markdown
## 避坑指南（Gotchas）

- `users` 表使用的是软删除（soft deletes）。查询时必须包含 `WHERE deleted_at IS NULL`，否则结果将包含已停用的账户。
- 用户ID在数据库中是 `user_id`，在认证服务中是 `uid`，在计费API中是 `accountId`。这三者指代的都是同一个值。
- 只要Web服务器在运行，`/health` 端点就会返回200，即使数据库连接已断开也是如此。请使用 `/ready` 来检查完整的服务健康状态。
```

请将这些避坑指南保留在 `SKILL.md` 中，以便Agent在遇到状况之前就能读取到它们。如果你告诉Agent何时去加载一个单独的参考文件，那也是可以的；但对于那些非显而易见的问题，Agent可能根本意识不到触发条件。

> 💡 **提示：**
> 当Agent犯了错误需要你纠正时，请将这个纠正添加到“避坑指南”部分。这是迭代提升技能质量最直接的方法之一（参见前文的“通过实际执行进行优化”）。

### 2. 输出格式的模板

当你需要Agent以特定的格式生成输出时，请提供一个模板。这比用散文式的语言描述格式更可靠，因为Agent非常擅长对具体的结构进行模式匹配。较短的模板可以直接写在 `SKILL.md` 中；对于较长的模板，或仅在特定情况下需要的模板，请将它们存储在 `assets/` 中，并在 `SKILL.md` 中引用它们，以便仅在需要时加载。

```markdown
## 报告结构

请使用此模板，并根据具体的分析情况调整各部分：

markdown
# [分析标题]

## 执行摘要
[用一段话概述主要发现]

## 主要发现
- 发现 1 及支持数据
- 发现 2 及支持数据

## 建议
1. 具体的可执行建议
2. 具体的可执行建议
```

### 3. 多步骤工作流的核对清单（Checklists）

显式的核对清单有助于Agent追踪进度并避免跳过步骤，特别是当步骤之间存在依赖关系或验证关卡时。

```markdown
## 表单处理工作流

进度：
- [ ] 步骤 1：分析表单（运行 `scripts/analyze_form.py`）
- [ ] 步骤 2：创建字段映射（编辑 `fields.json`）
- [ ] 步骤 3：验证映射（运行 `scripts/validate_fields.py`）
- [ ] 步骤 4：填写表单（运行 `scripts/fill_form.py`）
- [ ] 步骤 5：验证输出（运行 `scripts/verify_output.py`）
```

### 4. 验证循环（Validation loops）

指示Agent在进入下一步之前验证自己的工作。具体的模式是：执行工作 -> 运行验证器（可以是一个脚本、一份参考核对清单或是一次自检） -> 修复任何问题 -> 重复该过程直到验证通过。

```markdown
## 编辑工作流

1. 进行你的编辑工作
2. 运行验证：`python scripts/validate.py output/`
3. 如果验证失败：
   - 检查错误信息
   - 修复问题
   - 再次运行验证
4. 只有在验证通过后才继续后续操作
```

参考文档也可以作为“验证器”，指示Agent在最终定稿之前，对照参考文档检查自己的工作。

### 5. 计划-验证-执行（Plan-validate-execute）

对于批处理或具有破坏性的操作，请让Agent以结构化格式创建一个中间计划，对着事实的唯一来源（source of truth）进行验证，确认无误后再执行。

```markdown
## PDF 表单填写

1. 提取表单字段：`python scripts/analyze_form.py input.pdf` → `form_fields.json`
   （列出每一个字段的名称、类型以及是否为必填项）
2. 创建 `field_values.json`，将每个字段名称映射到其预期的值
3. 验证：`python scripts/validate_fields.py form_fields.json field_values.json`
   （检查表单中是否存在每个字段名称，类型是否兼容，以及必填字段是否缺失）
4. 如果验证失败，请修改 `field_values.json` 并重新验证
5. 填写表单：`python scripts/fill_form.py input.pdf field_values.json output.pdf`
```

这个流程的关键因素是步骤3：一个验证脚本，用于对照事实的唯一来源（`form_fields.json`）检查计划（`field_values.json`）。诸如“未找到字段 'signature_date' ， 可用字段有：customer_name, order_total, signature_date_signed”这样的错误提示，足以为Agent提供自我纠正所需的信息。

### 6. 打包可复用的脚本

在迭代优化某项技能时，通过跨测试用例比较Agent的执行轨迹。如果你发现Agent在每次运行时都在独立重复发明相同的逻辑，比如生成图表、解析特定格式、验证输出，这就是一个信号：你应该将该逻辑编写成一个经过测试的脚本，并打包存放在 `scripts/` 目录中，一次编写，反复使用。

有关设计和打包脚本的更多内容，请参阅“在技能中使用脚本”相关文档。

## 六、 下一步行动

当你拥有了一项可以运行的技能后，以下两步骤可以帮助你进一步完善它：

* **评估技能输出质量** （https://agentskills.io/skill-creation/evaluating-skills）， 建立测试用例，对结果进行评分，并系统性地进行迭代。
* **优化技能描述** （https://agentskills.io/skill-creation/optimizing-descriptions）， 测试并改进你的技能的 `description` 字段，以便它能在正确的提示（prompts）下被触发。
