
# MCP Tools and Capabilities


### 1. Dynamic Tool Registration & Authentication
- **Question:** How are dynamically registered MCP tools authenticated, verified for integrity, and authorized before being successfully added to the system's available toolset?
  - **Recommended Control:** Implement strict cryptographic signing or mutual TLS (mTLS) for tool registration endpoints. Enforce an allowlist of trusted tool repositories/publishers, and mandate an administrative Role-Based Access Control (RBAC) approval workflow before a dynamic tool becomes active.
  - **Associated Risk:** Without verification, an attacker (or a compromised internal service) could dynamically register a rogue "shadow tool." This allows the attacker to hijack AI requests, steal the user's data context, or force the agent to execute malicious payloads under the guise of a legitimate capability.

### 2. Agent-Skills Discovery Surface & Access Control
- **Question:** For systems with an active agent-skills discovery surface (e.g., using `tools/list`), how is tool visibility restricted so that agents only discover tools that the currently authenticated human user is authorized to execute?
  - **Recommended Control:** Enforce contextual, user-bound access controls at the MCP discovery layer. The MCP server must dynamically filter the tool manifest based on the authenticated user's session token and permissions, completely hiding unauthorized tools from the agent's context window.
  - **Associated Risk:** If discovery is globally exposed (or shared across a multi-tenant environment), the AI agent might hallucinate or be manipulated into discovering and executing administrative tools on behalf of a low-privileged user, leading to horizontal or vertical privilege escalation.

### 3. Execution Environment & Payload Sandboxing
- **Question:** How are the inputs (arguments) generated by the LLM, and the code executed by dynamically registered tools, sanitized and isolated to prevent system compromise?
  - **Recommended Control:** Treat all LLM-generated arguments as untrusted external input. Enforce strict JSON Schema validation and type checking before passing arguments to the tool. Execute dynamic tools within ephemeral, heavily restricted sandboxes (e.g., minimal Docker containers, WebAssembly/WASM) with no access to the host operating system.
  - **Associated Risk:** A successful Prompt Injection attack could manipulate the LLM into passing malicious shell commands, SQL injections, or scripts into the tool arguments. Without sandboxing, this results in Remote Code Execution (RCE) on the MCP server.

### 4. Excessive Agency & Human-in-the-Loop (HITL)
- **Question:** What mechanisms ensure that dynamically discovered tools capable of state-changing, destructive, or high-impact actions (e.g., mutating databases, sending emails, changing permissions) cannot be executed autonomously by the agent?
  - **Recommended Control:** Categorize tools by risk level. Implement a mandatory Human-in-the-Loop (HITL) approval gateway for all high-risk or state-changing MCP tools. The system must pause execution, present the exact arguments to the human user, and require explicit cryptographic consent before proceeding.
  - **Associated Risk:** Giving an AI agent autonomous execution rights over dynamic tools introduces "Excessive Agency." An LLM hallucination or an adversarial prompt could trigger a cascading sequence of destructive actions, such as mass-deleting infrastructure or exfiltrating sensitive data to third parties, without human intervention.

### 5. Network Security & SSRF Prevention
- **Question:** How is network egress controlled for MCP servers hosting dynamically registered tools, specifically to prevent unauthorized access to internal network infrastructure or cloud metadata services?
  - **Recommended Control:** Deploy MCP tool execution environments in isolated network segments (VPCs). Implement strict egress filtering (e.g., using network policies or proxies) to block access to internal IP ranges (RFC 1918) and cloud Instance Metadata Services (IMDS, e.g., `169.254.169.254`). 
  - **Associated Risk:** If an AI agent has access to a tool that makes web requests (e.g., a dynamic "URL fetcher" tool), an attacker can use prompt injection to force the agent into performing Server-Side Request Forgery (SSRF). This allows the attacker to pivot into the internal network, mapping microservices or stealing cloud IAM credentials.

### 6. Systems Without Active Discovery (Static Mapping Security)
- **Question:** In deployments *without* an active discovery surface (where tools are statically mapped to the agent), how does the system prevent the agent from attempting to invoke tools outside of its predefined functional scope?
  - **Recommended Control:** Enforce strict allowlisting at the MCP routing/execution layer. Even if the LLM hallucinates a tool call that is not in its static prompt, the MCP server must rigidly reject any `tools/call` request that does not match the hardcoded, pre-approved manifest for that specific agent.
  - **Associated Risk:** Relying solely on the LLM's system prompt to restrict tool usage is insufficient. Attackers can use jailbreak techniques to convince the LLM to guess and call hidden, unmapped, or administrative tools that happen to exist on the same MCP server backend.

### 7. Tool Data Exfiltration & Output Redaction
- **Question:** How is sensitive data protected when returned from an internal MCP tool back to the LLM or external agent context?
  - **Recommended Control:** Implement Data Loss Prevention (DLP) and redaction filters on the *output* of MCP tools before the data is sent back to the LLM. If the LLM is hosted externally (e.g., a third-party API like OpenAI or Anthropic), ensure no PII or highly confidential data is transmitted unless explicitly covered by a zero-retention Data Processing Agreement.
  - **Associated Risk:** An authorized dynamic tool might legitimately query a database and pull massive amounts of PII into the AI's context window. If this context is processed by an external, multi-tenant LLM provider, it constitutes a massive data breach and a violation of data residency controls.

### 8. Auditing & Forensics of Agent Tool Chains
- **Question:** How are the agent's intent, the tool discovery process, and the dynamic tool execution payloads logged to ensure forensic traceability during a security incident?
  - **Recommended Control:** Maintain immutable, centralized audit logs tracing the entire lifecycle of a tool invocation. Logs must include: User ID, original user prompt, AI system prompt, `tools/list` results presented to the AI, `tools/call` exact JSON arguments, execution duration, and the tool's response.
  - **Associated Risk:** AI decision-making is inherently opaque. If a dynamically registered tool causes a system failure or data breach, the lack of end-to-end cryptographic traceability makes it impossible to determine if the root cause was a user error, an LLM hallucination, a malicious prompt injection, or a compromised dynamic tool.
