

# check pointer
The Core Concept: Checkpointers
In LangGraph, a checkpointer is responsible for saving the state of your graph at each step. This is what gives an AI agent "memory" so it can remember previous messages in a conversation.

MemorySaver: This is a simple, built-in checkpointer that saves the graph's state in the server's RAM (memory).

If you are deploying this code to LangGraph Cloud or running it in LangGraph Studio, the platform automatically handles state persistence for you (usually using a robust database like PostgreSQL behind the scenes). If you hardcode a local MemorySaver here, it will conflict with the platform's built-in database, and your agent will lose its memory whenever the server restarts.

```
# Check if we're running in LangGraph API mode
if os.environ.get("LANGGRAPH_FASTAPI", "false").lower() == "false":
    # When running in LangGraph API, don't use a custom checkpointer
    graph = workflow.compile(**compile_kwargs)
else:
    # For CopilotKit and other contexts, use MemorySaver
    from langgraph.checkpoint.memory import MemorySaver

    memory = MemorySaver()
    compile_kwargs["checkpointer"] = memory
    graph = workflow.compile(**compile_kwargs)

```

# CopilotRuntime

`CopilotRuntime` **专门用于管理和运行不同的 agent** 的逻辑。它其实是一个“Runtime 容器”，负责把你的 agent 配置、调度和执行流程统一起来。我们可以拆开理解它的职责：

---

## 1️⃣ CopilotRuntime 的核心作用

1. **管理 agent 实例**

   * 你在初始化 `CopilotRuntime` 时，会传入多个 agent：

     ```ts
     const runtime = new CopilotRuntime({
       agents: {
         research_agent: new LangGraphAgent({...}),
         research_agent_google_genai: new LangGraphAgent({...}),
       },
     });
     ```
   * 每个 agent 都是独立的逻辑单元，可能是：

     * `LangGraphAgent`：直接调用 LangGraph 的图模型部署
     * `LangGraphHttpAgent`：通过 HTTP 调用远程服务
   * `CopilotRuntime` 负责统一管理这些 agent 的生命周期和调用接口。

2. **路由请求到正确的 agent**

   * 当你调用 `handleRequest(req)` 时，`CopilotRuntime` 会根据请求的上下文或者参数，把请求分发给正确的 agent。

3. **统一上下文管理**

   * 它可以处理跨 agent 的 session、memory 或者 runtime 配置（例如 deploymentUrl、API key 等）。
   * 保证每个 agent 在调用时拿到正确的配置和上下文。

4. **和 Next.js App Router 的集成**

   * 使用 `copilotRuntimeNextJSAppRouterEndpoint({ runtime, ... })` 后，`CopilotRuntime` 就可以直接处理 `req` 对象，生成响应，无需在 API route 内写重复逻辑。

---

## 2️⃣ 实际理解

可以把 `CopilotRuntime` 想象成 **一个 agent 的“操作系统”**：

* 它不会直接做 AI 推理或搜索，而是：

  * 管理 agent 的创建
  * 调度请求
  * 保证配置一致
* 真正的逻辑由 `LangGraphAgent` 或 `LangGraphHttpAgent` 实现。

---

## 3️⃣ 简单类比

| 角色               | 作用                                |
| ---------------- | --------------------------------- |
| `LangGraphAgent` | 单个 agent，定义任务逻辑，比如搜索或生成           |
| `CopilotRuntime` | 管理多个 agent，把请求路由给合适的 agent，并统一上下文 |
| `handleRequest`  | 将 HTTP 请求转成 agent 执行，并返回结果        |

---


**`CopilotRuntime` 专门处理 agent 的管理和调度逻辑，但它本身不做 AI 推理，推理逻辑在各个 agent 里。**

---

# 如何在 Next.js API Route（app router）里管理多个 endpoint 的 runtime
每个 endpoint 一个 POST 方法

在 app/api/copilotkit/research_agent/route.ts：
~~~
export const POST = async (req: NextRequest) => {
  const runtime = new CopilotRuntime({ ... });
  const { handleRequest } = copilotRuntimeNextJSAppRouterEndpoint({
    runtime,
    serviceAdapter: llmAdapter,
    endpoint: "/api/copilotkit/research_agent",
  });
  return handleRequest(req);
};
~~~

~~~
export const POST = async (req: NextRequest) => {

~~~

❌ 缺点：如果有很多 endpoint，会生成很多文件，管理上稍显繁琐。

## useAgent
调用 useAgent 时通常会这样：
~~~
import { EventType, useAgent } from '@copilotkit/react-core/v2';
import { useEffect, useState } from 'react';

export const useAgentRunErrorHandler = () => {
  const [agentRunError, setAgentRunError] = useState<string | null>(null);
  const { agent } = useAgent();

  useEffect(() => {
    if (!agent) return;

    const subscription = agent.subscribe({
      onRunInitialized: () => {
        setAgentRunError(null);
      },
      onRunErrorEvent: ({ event }) => {
        if (event.type === EventType.RUN_ERROR) {
          setAgentRunError(event.message);
        }
      }
    });
    return () => {
      subscription.unsubscribe();
    };
  }, [agent]);

  return { agentRunError };
};

~~~

## useEffect
React 组件的核心任务是根据数据（State/Props）渲染 UI。这个过程应该是“纯净”的。
但实际上，我们在写代码时，经常需要和“组件外部”的世界打交道，这些操作就被称为副作用。

useEffect 就是 React 提供给你专门用来写“副作用”代码的地方。常见的副作用包括：
- 发起网络请求（Fetch API 获取数据）
- 操作浏览器的原生 API（比如修改网页标题 document.title）
- 设置定时器（setTimeout 或 setInterval）
- 订阅事件或 WebSocket连接（比如监听窗口滚动、实时聊天消息）
简单来说，只要你的代码不仅仅是为了计算并在屏幕上画出 HTML，而是去动了外面的东西，它就应该放在 useEffect 里。

你可以（也应该）按照业务逻辑的用途，将代码拆分成多个 useEffect。React 会按照代码编写的顺序依次执行它们。


~~~

  useEffect(() => {

  }, [agent]);

~~~
这是一个非常核心的 React Hook 语法。我们可以把它翻译成一句大白话：

> **“React，请执行大括号里的这段代码。但是，只有在 `agent` 这个变量发生变化的时候，你才去执行它。”**

为了让你彻底明白，我们把这个语法拆解成 **左右两部分** 来详细解释：

---

### 第一部分：你要做什么？ (`() => { ... }`)

```javascript
useEffect( () => {
    // 这里是你想要执行的代码逻辑 (副作用)
    // 比如：发起网络请求、绑定事件、打印日志等
} , ...);
```
这是 `useEffect` 的第一个参数，是一个**箭头函数**。
它定义了你具体想要执行的任务。你可以把它理解为**“行动方案”**。

---

### 第二部分：什么时候做？ (`[agent]`)

```javascript
useEffect( ..., [agent] );
```
这是 `useEffect` 的第二个参数，叫做**依赖项数组 (Dependency Array)**。
它是这个语法的**灵魂**，你可以把它理解为 React 的**“监控探头”**。

数组里面写的变量（这里是 `agent`），就是 React 需要死死盯着的目标。

它的工作机制如下：
1. **第一次加载页面时**：React 会毫无条件地执行一次第一部分的“行动方案”，并且把当前的 `agent` 的值偷偷记录下来（记在小本本上）。
2. **以后每一次页面重新渲染时**：React 都会去检查这个“监控探头”。
    * 它会拿出当前的 `agent`，和它小本本上记录的“上一次的 `agent`”进行对比。
    * **如果发现两人一模一样**：React 就会说：“哦，`agent` 没变，那我就**不执行**行动方案了，跳过跳过，节省性能。”
    * **如果发现不一样了**（比如 `agent` 从 `null` 变成了一个真正的对象，或者换了一个新的实例）：React 就会说：“哎呀，`agent` 变了！我必须**重新执行**一次行动方案！”执行完后，再把新的 `agent` 记录到小本本上。

---

### 为什么要这么设计？（对比来看就懂了）

假设我们没有这个 `[agent]` 会怎样？你可以对比下面三种写法的区别：

#### 1. 不传第二个参数（极其危险 ❌）
```javascript
useEffect(() => {
  console.log("执行了！");
}); // 注意：这里没有数组
```
**结果**：只要组件里任何一个数据（State）发生哪怕一点点变化（比如用户在输入框打了一个字，或者秒表走了一秒），这段代码就会疯狂执行。极其浪费性能，甚至会导致死循环崩溃。

#### 2. 传一个空数组 `[]`（只做一次 ✅）
```javascript
useEffect(() => {
  console.log("执行了！");
}, []); // 监控探头里什么都不写
```
**结果**：React 只在组件**第一次出现在屏幕上**时执行一次。之后无论发生什么，它都**永远不再执行**。这通常用来做“页面刚加载时的初始化”（比如发一次网络请求拿文章列表）。

#### 3. 传变量 `[agent]`（精准打击 ✅ —— 就是你问的这个语法）
```javascript
useEffect(() => {
  console.log("执行了！");
}, [agent]); // 监控 agent
```
**结果**：做到了**精准控制**。
* 页面里别的变量（比如 `inputText`, `count` 等）怎么变，它都不管，坚决不执行。
* **只有** `agent` 这个变量变了，它才乖乖执行一次。

### 总结
`useEffect(() => { ... }, [agent]);` 是一种**性能优化**和**精准控制逻辑**的手段。它确保了与 `agent` 相关的复杂逻辑（比如上一问中的事件监听），**仅仅**在 `agent` 真的发生改变时才去运转，不多跑一次，也不漏跑一次。




## agent ID
如何在 CopilotKit Runtime 定义 agent（agentId）

你需要在你的 backend runtime 里配置一个 CopilotRuntime 实例，并把 agent 映射到一个 key，例如：

🚀 这个例子来自实际用法（Next.js API route + HttpAgent）：

📌 示例（Next.js API: app/api/copilotkit/route.ts）
~~~
import { CopilotRuntime, HttpAgent } from "@copilotkit/runtime";
import { NextRequest } from "next/server";

const runtime = new CopilotRuntime({
  agents: {
    // 👇 这里 key 就是 agentId
    default: new HttpAgent({
      url: "http://localhost:8000/agent", // 对应你的后台 AG‑UI agent 服务
    }),
  },
});

export async function POST(req: NextRequest) {
  const { handleRequest } = runtime.streamHttpServerResponse(req);
  return handleRequest();
}
~~~
agents.default: 这是你定义的 agent key（也就是 agentId）  
HttpAgent({ url }): 这是 agent 的执行端，用来与后端 agent 服务（实现了 AG‑UI 协议）通讯  
请求到这个 API 时，CopilotRuntime 会把事件流转发回前端 UI 进行渲染/响应。

前端怎么和这个 agentId 连接

在 React 组件里：
~~~
import { useAgent } from "@copilotkit/react-core/v2";
function MultiAgentView() {
  const { agent: primary } = useAgent({ agentId: "primary" });
  const { agent: support } = useAgent({ agentId: "support" });
  return (
    <div>
      <div>Primary: {primary.messages.length} messages</div>
      <div>Support: {support.messages.length} messages</div>
    </div>
  );
}
~~~

useAgent.agentId 必须匹配 runtime 配置里的 key  
这会建立前端和 backend agent 之间的事件流连接  
visibleMessages 自动监听并渲染从 agent 流过来的消息（包括 streaming tokens）  

## UseAgent

~~~
import { useAgent, UseAgentUpdate } from "@copilotkit/react-core/v2";
// Only re-render when messages change
function MessageCount() {
  const { agent } = useAgent({
    updates: [UseAgentUpdate.OnMessagesChanged]
  });
  return <div>Messages: {agent.messages.length}</div>;
}
~~~
updates 参数:
这是性能优化的核心。默认情况下，useAgent 可能会监听 Agent 状态的所有变化（比如某个内部变量 isThinking 的改变）。  
通过传入 [UseAgentUpdate.OnMessagesChanged]，你订阅了一个特定的事件。只有当 agent.messages 数组的内容发生变化时（例如：收到新消息、消息被截断等），MessageCount 组件才会重新渲染。  
agent 对象:
从 Hook 中解构出的 agent 对象包含了该 Agent 的当前快照。
agent.messages：存储了与该 Agent 交互的所有对话记录。

## useAgentContext
Basic Usage
~~~
import { useAgentContext } from "@copilotkit/react-core/v2";

function UserGreeting({ user }: { user: { name: string; role: string } }) {
  useAgentContext({
    description: "The currently logged-in user",
    value: { name: user.name, role: user.role },
  });

  return <div>Welcome, {user.name}</div>;
}
~~~

这段代码展示了 CopilotKit v2 中的 Context Injection（上下文注入） 机制。它的核心作用是让 AI Agent “看见”当前应用中的实时数据。  
以下是详细解释：
1. 代码功能解释
useAgentContext 的作用是将前端的 React 状态或数据“喂”给 AI Agent。  
description: 这是给 AI 看的描述。它告诉 Agent 这一段数据是什么。在这个例子中，它告诉 AI：“这是当前登录用户的信息”。  
value: 这是实际传递给 AI 的数据对象。AI 在决策或生成回复时，可以引用 name 和 role。  
效果：当用户问 AI “我是谁？”或者“以我的权限能做什么？”时，AI 能够根据 useAgentContext 注入的 value 给出准确回答，因为它已经把这些数据纳入了它的上下文。  
2. user 是在哪里赋值的？  
在你的代码片段中，user 是通过 React Props（组件属性） 传入 UserGreeting 组件的。  

在你的代码之外，一定有一个地方调用了 <UserGreeting /> 并传递了 user 对象：  

~~~
// 父组件
function App() {
  const currentUser = { name: "张三", role: "管理员" }; // 这里是赋值的地方

  return (
    <div>
      <UserGreeting user={currentUser} />
    </div>
  );
}
~~~

## runtimeUrl 和 Provider

为了前端 useAgent 能正常工作，还要在 App 里用 CopilotKit Provider 组件 指定 runtimeUrl（也就是指向你上面定义 runtime API 的 endpoint）：

~~~
import { CopilotKit } from "@copilotkit/react-core/v2";

function App({ children }) {
  return (
    <CopilotKit
      runtimeUrl="/api/copilotkit"
      // 可选： headers、credentials 等
    >
      {children}
    </CopilotKit>
  );
}

~~~
这样所有 Hooks/组件都知道要向哪个 endpoint 去连接 backend runtime。
