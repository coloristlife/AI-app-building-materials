## 一、 架构的鸟瞰图 (Bird's-eye view of the architecture)

首先，让我们快速从全局视角看看整个架构和结构。你会发现它的组件其实非常简单。

最核心的部分是 **AI 智能体核心（AI Agent Core）**，也就是它的“智能代理循环（Agentic Loop）”。要连接到这个核心，有多种不同的方式：
1. **CLI（命令行界面）**：你只需在命令行中输入 `Hermes` 即可与你的 AI 智能体连接。
2. **网关（Gateway）**：这是一个始终在运行的系统，允许你通过 Telegram、电子邮件、Slack 等消息服务连接到 Hermes。它是你连接各类消息平台的桥梁。
3. **API**：你也可以通过 API 进行连接。

所有这些连接方式最终都会汇总，让你能够与作为系统核心的 AI 智能体进行交互。

围绕着这个 AI 智能体，还有许多它预装并开箱即用的配套服务：
*   **工具（Tools）**：它拥有大量可用的工具。
*   **技能（Skills）**：它也具备一系列可调用的技能。
*   **记忆（Memory）**：这是一个非常有趣的设定。Hermes 的记忆分为两个不同的部分：
    *   **外部记忆（External Memory）**：这通常由外部提供商支持，例如 Mem0、SuperMemory 等，我们会在后面详细讨论。
    *   **内部记忆（Internal Memory）**：本质上就是你的会话记录（Session transcripts）。每次对话都会以会话记录的形式存储在智能体的内部记忆中。
*   **其他配置文件**：它可以修改诸如 `soul.md` 和 `user.md` 这样的文件。这些文件主要向智能体提供关于“它自己的个性”以及“当前正在使用它的用户”的信息。

这就是整个系统的主要元素。如你所见，它其实非常简单，接下来我们将更详细地逐一拆解。

## 二、 代理循环 (Agent Loop)

现在我们来仔细看看 Hermes 内部的代理循环。

这个循环非常简单，与你在其他极简风格的智能体（比如 PyAgent、OpenCode 等）中看到的架构非常相似。它的简单之处在于，**每当用户发送一条消息，这个循环系统就会完整执行一次**：

1.  **用户发送消息**：第一步，用户输入并发送信息。
2.  **构建上下文（Build Context）**：Hermes 会从它所有的内部记忆和预设的提示词中构建上下文。这些上下文和历史消息（包括系统提示词、`soul.md` 文件、`user.md` 文件、消息历史等）将会被打包。
    *   *注：`soul.md` 是一个赋予智能体个性的 Markdown 文档（例如设定它的灵感来源、语气等）；`user.md` 则是对使用者（也就是你）的描述。*
3.  **发送至 LLM**：整个上下文被发送给大型语言模型（LLM）。
4.  **调用工具（Tool Call）**：LLM 可以决定是否调用工具。如果它决定调用，系统就会执行该工具（比如：网络搜索、写入文件、读取文件或更新文件系统中的文件），并将结果反馈给 LLM。只要 LLM 认为有必要，这个调用工具的循环就会一直持续下去。
5.  **最终响应（Final Response）**：完成所有需要的工具调用后，它会给你一个最终的回复。
6.  **记忆更新（Memory Update）**：这是循环中至关重要的最后一步。系统会指示智能体分析刚才的消息，看看是否有任何值得记住并写入记忆的信息。这使得智能体能够在整个交互过程中不断学习，当你下次询问类似问题时，它已经掌握了相关背景。正是这个环节，让 Hermes 成为一个随着使用次数增加而不断学习和进化的智能体。

## 三、 上下文构建 (Context)

了解了代理循环后，我们来单独详细聊聊它组装的“上下文”。在构建智能体时，这非常重要。

Hermes 的上下文非常直接且极简，主要由几个 Markdown 文件组成：

*   **`soul.md`（智能体个性）**：这是你设定智能体希望使用什么语气、什么能启发它、它的目标是什么、它对待你的态度，以及任何你希望它表现出的行为的地方。如果你看过 Claude 那些写得很优美的长篇系统提示词，这正是你需要在这里写的东西（而且你应该为自己量身定制）。需要注意的是，当你刚安装 Hermes 时，这个文件通常是完全空白的。如果你不手动设置或让 Hermes 自己写，它将被默认的系统提示词取代（默认提示词只会简单告诉它：你是 Hermes，一个永远在线的虚拟助手等）。但你绝对会想要拥有自己的 `soul.md` 来打造专属的智能体。
*   **内存目录（Memory Directory）下的文件**：
    *   **`user.md`**：与 `soul.md` 不同，每当 Hermes 在对话中了解到关于你的信息时，它会**自动更新**这个文件。例如，你告诉它：“对了，我是一名软件工程师，我正在开发这个”，或者“我是一名市场分析师，我正在做这个”。智能体一旦识别出这是关于你个人的信息，就会把它存储在这里（提取自对话的用户信息）。
    *   **`memory.md`**：这是一个关于任意事实的记忆库。智能体会手动更新它（除非你要求它自己更新，或者你亲自去修改）。这里存储的不一定是关于你的信息，而是它在与你对话过程中学到的关于如何使用工具、不同的工作流，或任何它觉得有趣、有用的任意事物。它会根据 `soul.md` 中设定的目标，把这些信息保存在这里。

除了这些 Markdown 文件，上下文中通常还包含：
*   **过去线程/会话的信息摘要**：**但这仅在你设置了“外部记忆”时才会出现。** 如果未设置，默认不会有这一项。这主要是一些可能与当前对话相关的过去对话的摘要。
*   **技能描述和工具描述**。
*   **最新的互动消息**：如果是短对话，会包含整个对话；如果对话超过了智能体上下文窗口的特定阈值，Hermes 会对对话进行总结（Summary），并将总结提供给上下文。

## 四、 上下文压缩 (Context compression)

既然谈到了上下文，现在是聊聊“上下文压缩”的最佳时机。

当你与大语言模型对话时，总会有一个特定的上下文窗口限制（通常在 25 万到 100 万个 Tokens 之间）。在设置 Hermes 时，系统会问你希望何时触发消息历史记录的压缩。

**默认情况下，压缩会在占用上下文 50% 时触发。** 如果你使用了 50% 的上下文，Hermes 就会触发压缩函数，总结所有以前的消息，将该摘要追加到上下文中，并用这个摘要替换掉之前的消息。当然，这是高度可定制的。如果你使用的是较小的模型或上下文窗口不大的模型，你也可以在详细设置时将其调整为 70% 或 80%，这或许是更好的选择。

那么，它到底在何时检查并进行压缩呢？主要在**两个时刻**：
1.  **每次轮次之前（Before each turn）**：也就是在调用语言模型发送下一条消息之前。
2.  **发生错误时（On error）**：每当 LLM 返回有关上下文窗口超出限制的错误时。

**它是如何计算 Tokens 的？**
这分为两种情况：
1.  **第一条消息**：因为还没有发送任何内容给 LLM，所以没有关于当前上下文有多少 Tokens 的数据。虽然你可以使用一个本地的分词器（Tokenizer），但这太耗费资源了。所以他们用了一个更简单直接的方法：**将总字符数除以 4**，作为近似的上下文大小。如果这个近似值超过了你设置的 50% 阈值，就会触发摘要压缩。
2.  **后续消息**：当 LLM 给你返回答案时，响应中会包含一个 `usage`（用量）参数（包含输入和输出的 Tokens，具体取决于 LLM 提供商）。将这些数字相加即可获得最准确的 Token 描述，因为这直接使用了模型自己的分词器。使用这个方法既足够精确，又不会像在每一步都运行本地分词器那样昂贵。

### 上下文压缩提示词 (Context compression prompt)
如果你对它实际用于压缩的提示词感兴趣，你可以在 `context_compressor.py` 文件中找到它（大概在第 1400 行左右，不过每次代码重构行号会有变化）。

它的提示词要求 LLM 总结整个内容，并在摘要中创建多个不同的特定部分，例如：**整体目标（full goal）、限制条件（constraints）、已完成的操作（completed actions）、活动状态（active state）、历史进度（historical progress）、智能体目前受阻的地方（blocked on）、做出的关键决策（key decisions）、已解决的问题（resolved questions）、相关文件（relevant files）、关键上下文（critical context）、先前的摘要（previous summaries）、下一步要合并的轮次（next turns to incorporate）以及要总结的轮次（turns to summarize）**等。

如你所见，它包含了非常多细节，相比于像 Pi 这样架构中极简的总结提示词，Hermes 的提示词要丰富得多，它能给智能体提供更充足、更有必要的当前状况上下文。

## 五、 网关系统 (Gateway)

虽然网关不一定是 Hermes 中最困难或最复杂的部分，但我认为**正是网关让 Hermes 变得如此主流和受欢迎**。

网关是一个允许你通过各种消息平台（如 Telegram、WhatsApp、电子邮件、短信、Slack、Discord 等）与智能体交谈的系统。

**它是如何工作的？**
首先，网关启动一个 `asyncio` 循环，持续运行并等待/轮询不同的网关接口。每一个第三方网关的集成都有自己独特的轮询方式：
*   有些使用 Webhooks。
*   有些（比如 Telegram）则是一个每秒运行一次的小循环，不断轮询 Telegram API 查看聊天机器人是否有新消息。
*   有些使用 Websockets。

正因如此，每一个第三方网关的集成都需要独立配置。这并不是一个默认对所有平台通用的网关。你需要通过命令行（例如 `Hermes setup gateway` 设置 Telegram），然后配置你的 Bot ID，以及允许与 Hermes 交互的 User ID 等。

**构建上下文（Construct Context）**
网关不仅负责接收消息，它还需要从头构建消息对话和上下文。因为当网关（比如从 Telegram）收到消息时，它接收到的只是一条单条消息，而不是完整的对话历史。

它通过一个存储在本地的 **SQLite 数据库** 来拼凑历史记录。它如何识别呢？
你的消息历史记录标识符的第一部分将是网关名称的前缀（例如 `telegram`），接着附加 Telegram 返回的 Session ID（会话 ID），以及其他一些 ID 来构建完整的标识符。

当收到新消息时，网关会带上这个前缀和 Session ID，去 SQLite 数据库中查询该对话的所有历史消息，然后将它们追加到上下文中，最后才发送给你的 AI 智能体。所以，如果没有网关这样构建上下文，你就根本不会有消息历史记录。

**会话管理器（Session Manager）**
网关还有一个非常重要的会话管理器，它决定了你的消息何时、以何种方式到达大语言模型。
假设你在刚发送完一条消息、智能体正在处理时，紧接着又发了一条消息，会话管理器会决定是中断（interrupt）智能体、引导（steer）智能体，还是将消息排队（queue it up）。
这取决于你发送消息的方式。比如在 Telegram 中：
*   发送 `/interrupt` 将会中断它。
*   发送 `/steer` 将会引导它的方向。
*   如果只是像平时那样直接发送，它将会把消息排队。

这是一个非常有趣且实用的模块。你完全可以为其他种类的智能体编写你自己的网关，比如作者就在自己的 VPS 上运行了自己的 Pi 网关，从而可以通过 Telegram 与之交流。

## 六、 记忆系统 (Memory)

我们在前面已经零散地提到了记忆，但它绝对值得拥有一个专属的章节。在 Hermes 中，记忆主要以三种不同的方式存在：

1.  **Markdown 文件**：正如之前提到的，位于 `memory` 目录下的 `soul.md`、`memory.md` 和 `user.md`。它们总是紧跟在系统提示词之后附加到上下文窗口中。
2.  **SQLite 数据库**：所有的先前会话都不会作为 Markdown 文件存储。Hermes 有一个 SQLite 数据库，保存了你与它每次互动的每一条消息。它有许多不同的表、行和数据模型，但本质上都是**所有会话的完整文本记录（full transcripts）**。这也是网关拉取对话记录的地方。非常有趣的是，它甚至包含一个专门的**“纯文本（bare text）”表**，里面只包含所有对话的纯文本，目的是让对其执行相似性搜索（similarity search）变得非常简单。
3.  **外部记忆（External memory）**：这非常非常重要且有用。**外部记忆在默认情况下是不配置的**。它来自不同的外部提供商，Hermes 支持非常多此类服务，例如：
    *   **Mem0**（相信它使用的是相似性搜索）。
    *   **SuperMemory**（要求你在每个轮次后发送整个对话历史进行存储，并使用 LLM 提取正确的记忆）。
    *   **Honcho**。
    
    这些提供商都专门致力于为智能体提供智能或记忆。这里支持的许多外部记忆提供商实际上都是免费的，我强烈建议你去配置它们，因为这会极大地改善 Hermes 从你身上学习的方式。（未来我们甚至可以专门做一个视频来给这些系统排名，因为它们的差异很大，有的使用丰富的 LLM 查询，有的使用语义搜索等）。

**外部记忆的触发机制：**
当你设置了外部记忆后，它会在**第二条消息（即第一条消息之后）**查询该外部记忆。
运作逻辑是：假设你开始讨论一个新功能或新工作流，你发送第一条消息，LLM 给你回复。在第一条消息之前，它不会去查询数据库。但是，当智能体回复了第一条消息、知道了你在谈论什么之后，它就会去查询外部记忆系统，**试图猜测你的下一个问题会是什么**。这非常像人类的思考模式：当别人问你一个问题时，你一边回答，脑海中一边同时回忆过去关于这个话题的对话。

*使用技巧*：如果你启用了外部记忆，并且在与 Hermes 对话的第一次尝试中它没有想起某些事，你可以直接在第一条消息中描述你想让它想起什么，然后紧接着发一条跟进消息询问更多细节，这样它在第二条消息时就已经查询过外部记忆系统了。

## 七、 定时任务 (Cron Jobs)

最后，我们要讨论这种智能体中非常重要且极具特色的功能：定时任务（Cron jobs）。

如果你以前使用过服务器，你大概知道 Cron，它通常是一个每分钟运行一次的系统进程，提取该分钟计划执行的任务并执行它们。Hermes 也是类似的工作原理。不过请注意，**Hermes 中的 Cron 不与服务器的 Cron 进程绑定。**

在 Hermes 中，Cron 进程是它自己内部的一个循环，每分钟运行一次。每分钟，它会运行一个名为 `tick` 的函数，提取你在 cron jobs 中计划的任务，并在那一刻执行它们。

**什么是定时任务？**
它允许你让 Hermes 自动化一些任务。比如：
*   “每天早上给我发一封包含最新 AI 新闻的电子邮件。”
*   “每天在 Slack 上给我的社区发一条消息，告诉他们 AI 的新进展。”
*   “每个星期五给我的老板发一封电子邮件汇报工作。”

**它是如何存储的？**
这里文档的说明有些棘手。官方文档说 cron jobs 存储在 SQLite 中，但在实际分析代码和数据库时，并没有在 SQLite 数据库中找到它们。实际上，**定时任务是存储为纯 JSON 文件的**。
它的确切路径在：`.hermes/cron/jobs.json`。
这个 JSON 文件中列出了所有的定时任务及其对应的提示词、它应该做什么等信息。Hermes 每次 `tick` 时都会检查这个 JSON 文件，以弄清楚是否需要运行任务。你更新定时任务时，也是直接在这里更新。

在 `cron` 目录下，还有一个 `output` 目录。在其中你会发现一系列 Job ID 目录。在每个 Job ID 目录下，会有每一个具体执行轮次（run）的 Markdown 文件，里面存储了该任务执行的结果。

**关于通知的一个冷知识（Trivia）：**
Cron 任务并不会自动使用它那套“发送消息（send message）”的工具去给你发消息。当你在设置网关（比如 Telegram、Discord 或 Slack）时，系统会询问你是否希望将某个特定的网关（及该网关下的用户 ID）设为你的 **“主场（Home）”**。
实际发生的情况是：每当执行完一个定时任务，它会通过系统的原生通知机制，将通知消息投递到你的“主场”集成应用（你的首选消息应用）上，而不是让智能体去调用某个发送消息的工具。
