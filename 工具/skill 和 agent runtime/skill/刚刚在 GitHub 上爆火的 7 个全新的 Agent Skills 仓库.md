**以及它们到底能做什么**

2026年8月9日，GitHub Trending（趋势榜）前五名的仓库中有三个是 Agent Skills（智能体技能）的集合：`addyosmani/agent-skills`、`google/skills` 以及 `mattpocock/skills`。

其中一些项目是最近爆火的，而不是刚刚创建的。这份榜单快照衡量的是当前的关注度，而不是仓库的建立时间。

它们并不是三个新的基础大语言模型。它们是三个包含了 Markdown 指令、脚本和参考资料的集合，用于告诉现有的智能体（agents）如何执行特定的工作。这种区别很重要。模型的竞赛仍在继续，但开发者们越来越多地在问另一个问题：**我如何让智能体遵循我团队的实际工作流？**

Agent Skills 正在成为一种答案。这种开放格式以一个 `SKILL.md` 文件为核心，包含名称、描述和操作指令。一项技能还可以包含脚本、参考资料和资产组合。兼容的智能体可以先只发现技能的元数据，然后在任务匹配时再按需加载完整的指令。这种渐进式披露（progressive disclosure）使得庞大的目录不必在每次对话中都向大模型灌输所有的指令。

我查阅了这股热潮背后的仓库。这 7 个仓库之所以有用，原因各不相同。**不要把它们全部安装，要理解它们各自负责的是哪一个层面。**

### 1. `agentskills/agentskills` : 核心格式，而不是工作流包
当你想了解什么是真正的“可移植技能”时，你应该去阅读这个仓库。它包含了开放规范、文档、示例和验证工具。它的核心契约被刻意设计得很小：一个技能就是一个包含 `SKILL.md` 文件的目录。Frontmatter（前置元数据）让技能可被检索，而正文则解释了智能体应该做什么。

在以下情况你应该使用此仓库：
* 编写可以跨越各种兼容智能体运行的技能。
* 验证命名、结构和元数据。
* 构建内部技能目录，而无需自己发明专有格式。
* 理解“常驻指令”与“按需加载知识”之间的区别。

### 2. `addyosmani/agent-skills` : 软件交付操作系统
这是一个面向生产环境的工程包。它的技能涵盖了从定义问题到计划、构建、验证、审查和发布的整个路径。

这里有用的理念不是“更多的提示词”，而是“可复用的质量门禁”。一个编码智能体可以很快生成一个看似合理的补丁。而这个包试图让它在适当的时候慢下来：编写规范、使用测试驱动开发、有条理地调试、审查更改，并在宣布完成之前验证结果。
风险在于“流程过载”。一个小的错别字不需要经历五阶段的设计审查。采用某些特定技能的前提是它们能消除那些反复出现的故障，而不是因为这个仓库很火。

### 3. `mattpocock/skills` : 针对“真实”工程工作的主见实践
这个包内嵌了一系列实践操作，例如对设计进行盘问式审查、诊断 bug、测试驱动开发、领域建模、架构设计、研究以及代码审查。

一项“诊断技能”可以强制智能体在修复之前先收集证据。一项“领域建模技能”可以让智能体命名业务概念，而不是在代码库中散布随意的布尔值和字符串。对于经验丰富的开发者来说，这才是技能的真正价值所在：**它们可以把一位优秀的 Staff 级别工程师坚持要进行的对话逻辑给编码下来。**
代价是“主观性”。这些并不是普遍法则。请阅读每一项技能，并决定其工程品味是否与你的团队、架构和风险承受能力相匹配。

### 4. `google/skills` : 谷歌产品的官方知识
这是一个庞大的特定供应商目录，为 Google 产品和技术提供 Agent Skills。在我8月9日测试的版本中，它包含了 104 个 `SKILL.md` 文件，涵盖了 Google Cloud、GKE、BigQuery、Cloud Run、数据库、监控、广告产品以及相关工作流。

这不是一个通用的“让我的智能体变聪明”的打包文件。它是一个为已经在 Google 生态中工作的开发者准备的操作知识层。我检查的一些代表性的云技能在项目范围限定、检查叶子命令语法、缩小查询范围，以及在执行破坏性、IAM、计费、组织或密钥管理操作前进行主动询问方面都有明确指示。这就是云技能应当包含的约束。
没有必要在每个项目中安装全部 104 个技能，只挑选你正在使用的领域即可。

### 5. `vercel-labs/skills` : 分发层
`vercel-labs/skills` 解决的是另一个问题：在各个编码智能体之间寻找和安装技能（开放智能体技能工具 `npx skills`）。

它的命令行工具（CLI）支持添加、列出、查找、更新和初始化技能等命令。该项目表示支持 Claude Code、Codex、Cursor 及其他许多智能体。这一点很重要，因为只有当开发者能在不同的工具之间移动技能包、而无需每次重新构建安装工作流时，一个标准才是有价值的。
CLI 很方便，但方便并不能消除“信任边界”。一项技能可能包含操作指令和附带的脚本。在将其添加到一个敏感代码库之前，应当：
* 阅读 `SKILL.md`
* 检查每一个被引用的脚本
* 检查该工作流期望使用什么工具和凭据
* 固定（Pin）或记录你所审查过的 commit 版本
* 先在一个一次性的仓库中进行测试
**请把技能当作可执行的依赖项对待，而不是无害的代码片段。**

### 6. `NVIDIA/skills` : 经验证的供应商目录
`NVIDIA/skills` 展示了企业级目录应该是什么样子的（安装到编码智能体中以运行物理人工智能）。

NVIDIA 的文档描述了横跨其各大产品的技能，并在发布流程中加入了自动扫描和签名验证机制。其中最有趣的部分是“出处证明（provenance）”。如果智能体要配置底层基础设施、运行 GPU 工具，或者为专门的平台生成命令，那么“某人恰好写了这段 Markdown”绝对不是一个充分的信任模型。
发布者身份、更新历史、审查状态和完整性检查都成为了产品的一部分。这并不意味着每条指令在你的环境中都绝对正确，但它确实让指令来源的可靠性变得更容易推断。

### 7. `MicrosoftDocs/Agent-Skills` : 文档变为可操作对象
它将 Microsoft 和 Azure 的指导方针打包成了智能体可消耗的技能（指南精选自 Microsoft Learn）。

智能体在规划或实施时可以由此引入一个高度聚焦的工作流。但这里的危险是“悄无声息地过时”。云平台、CLI 工具、权限和定价都在变化。一个技能应该始终指回权威文档，并将“验证”作为工作流的一部分，而不是把记住的命令当作永恒的真理呈现。
同样的领域包模式在 Firebase 的官方技能仓库中也能看到。预计未来会有更多平台团队发布他们自己的官方版本。

### 这七个仓库背后的规律
这些仓库实际上占据了不同的分层：
1. **规范层**：定义技能是什么（`agentskills/agentskills`）
2. **工程实践层**：团队希望如何执行工作（`addyosmani/agent-skills`、`mattpocock/skills`）
3. **供应商专长层**：如何安全地使用特定平台（`google/skills`、`MicrosoftDocs`、`NVIDIA`）
4. **分发层**：技能如何在智能体之间流动（`vercel-labs/skills`）
5. **信任层**：发布者如何证明指令的来源（`NVIDIA/skills`）

这一技术栈分层比任何单一仓库的 Star 数量更重要。GitHub 的 Star 衡量的是关注度，而不是正确性。GitHub Trending 也只是一个波动剧烈的每日快照，并非质量指标。

### 我在采用一项技能前定下的规则
面对一个新技能，我不会问：“这个技能受欢迎吗？”，我会问：
* 这个技能可以防止什么反复出现的故障？
* 它假设自己拥有哪些权限？
* 它能访问哪些文件、工具、网络服务和凭据？
* 我怎么知道它已经正确完成了工作？
* 我刚才审查的是哪个 commit 版本？

## Skill 的效果严重依赖于 Runtime


**“Write once, run perfectly everywhere”（编写一次，随处完美运行）在当前的 Agent Skill 生态中是不存在的。** 一个 Skill 在 GitHub 上拥有 10,000 颗 Star，只能证明它在*某个特定的 Runtime（比如 Claude Code 或 Cursor）*下表现很好，并不意味着它能直接适用于 Goose、Aider 或其他任何 Agent Runtime。

这也是为什么在之前的讨论中，我强烈建议你**必须针对 Goose 自己写一个 Eval Harness 去跑 Benchmark**。

这里面有几个决定性的技术原因，导致了 Skill 的效果严重依赖于 Runtime：

### 1. 基础工具链（Capabilities / Tools）的差异
Skill 是一份“工作流说明书”（SOP），它经常会假定 Runtime 具备某些特定的“手脚”。
*   **假设：** 一个部署后端代码的 Skill 可能会在指令里写：“请使用终端（Terminal）执行 `docker build`，并监控输出流”。
*   **现实：** 如果你的 Runtime 是 **Goose**，它默认具有强大的本地 Bash 控制权，这个 Skill 就能完美运行；但如果你的 Runtime 是一个只允许修改文件、被沙盒限制的轻量级 Web Agent，这个 Skill 就会立刻崩溃。
*   **结论：** Runtime 必须提供 Skill 运行所需的特定工具（如文件读写、Bash 执行、或者特定的 **MCP Server**）。

### 2. 底层大模型的“智力”与“注意力”差异
即使所有的工具都齐备，不同的 Runtime 背后调用的 LLM（大语言模型）基座是不同的，或者 System Prompt 的设定是不同的。
*   **复杂指令跟随：** 像 `mattpocock/skills` 这种包含复杂“测试驱动开发（TDD）”流程的技能，需要模型有极强的逻辑规划和长文本注意力。它在基于 Claude 3.5 Sonnet 或 GPT-4o 的 Runtime 上可能表现神勇，但如果你的 Goose 配置的是一个本地的 8B 参数小模型，智能体可能在执行到第二步时就“忘了”规则，开始胡编乱造。
*   **输出格式偏好：** 不同的 Runtime 对 Markdown 解析、代码块包裹的要求不一样。Skill 可能要求“始终输出完整文件”，而某个 Runtime 为了省 token 强制要求模型“只输出 Diff 补丁”，这就会导致 Skill 逻辑冲突。

### 3. 上下文与记忆机制（Context Management）的差异
一个高级的技能（比如大型代码库的重构）通常需要多次对话（Turns）。
*   有的 Runtime 在达到上下文极限时，会聪明地总结历史并滚动向前（Rolling memory）。
*   有的 Runtime 拥有强大的向量检索（RAG），能记住几百步前的对话。
*   如果你把一个依赖长记忆的重型 Skill 放进一个每次对话只带最近 5 轮上下文的轻量级 Runtime 中，任务一定执行不下去。

### 打个比方：菜谱与厨房
*   **Skill（智能体技能）** = 菜谱（说明了要放几克盐、先炒后炖）。
*   **Agent Runtime** = 厨房 + 厨师。
*   **LLM 模型** = 厨师的智商。
*   **Tools (工具/MCP)** = 厨房里的设备（烤箱、切肉机）。

`AgentSkills` 等开源规范目前解决的只是“**让菜谱的排版格式标准化**”（大家统一使用 `SKILL.md`），让所有的厨师都能看懂标题和步骤。但这解决不了“你的厨房里没有烤箱”或“你的厨师不会颠勺”的问题。

### 总结：这对你的启发是什么？

这就是为什么各大厂商都在推行 **MCP (Model Context Protocol)**——为了尽量拉齐各大“厨房”的设备标准。

这也证明了你目前建立评估体系的思路是极其正确的：**不要轻信任何开源技能的通用疗效**。当你从 GitHub 上下载了 `addyosmani/agent-skills` 里的某一项技能并准备给你的团队使用时，必须把它放进你的**Goose Eval Harness** 里，在你们实际配置的模型底座和工具链下跑一遍，看看 Benchmark 的通过率到底是多少。

**评测环境，必须紧贴你的运行时环境。**
