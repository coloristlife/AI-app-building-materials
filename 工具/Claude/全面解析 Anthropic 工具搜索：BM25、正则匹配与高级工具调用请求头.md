Anthropic 的“工具搜索（Tool Search）”功能让 Claude 能够按需发现工具——通过 `tool_search_tool_bm25_20251119`（自然语言）或 `tool_search_tool_regex_20251119`（模式匹配）变体来实现——而不是一次性在前端加载每一个工具定义。这项功能需要使用 `advanced-tool-use-2025-11-20` 测试版请求头（beta header），并且支持 Claude Sonnet 4.5+ 和 Opus 4.5+ 模型。我一直在测试这项功能，虽然它的发展方向令人期待，但我现在还不打算将其部署到生产环境中。以下是营销团队在实施该功能前需要了解的关键信息。

Growth Method 已经在使用 Claude 的工具调用功能，通过自然语言从 PostHog 和 GA4 获取分析数据。当 Anthropic 宣布将“工具搜索”作为其高级工具调用功能的一部分时，我看到了它为那些正在应对臃肿技术栈的营销团队带来的巨大潜力。然而，现实情况还远未达到它的承诺。

### 工具搜索究竟是如何工作的？

工具搜索解决了一个切实存在的问题：**上下文窗口膨胀**。标准的工具调用会在一开始就将所有的工具定义加载到 Claude 的上下文窗口中。如果你有 50 个工具，这意味着在你还没开始任何实际工作前，就已经消耗了大约 10,000 到 20,000 个 Token。

工具搜索反转了这一过程。Claude 会动态搜索你的工具目录，并且只加载它所需要的内容。你在 API 请求中将工具标记为 `defer_loading: true`，然后 Claude 就会通过正则模式匹配或 BM25 自然语言搜索，按需发现它们。

当你启用工具搜索时，Claude 最初只能看到搜索工具本身以及任何未被延迟加载的工具。当它需要其他工具时，它会使用诸如 "weather"（正则变体）或像“用于发送电子邮件的工具（tools for sending emails）”（BM25 变体）之类的自然语言查询来进行搜索。API 会返回 3 到 5 个相关的工具引用，并将它们自动扩展为完整的工具定义。

---

### 两种搜索变体

Anthropic 提供了两种搜索途径。**正则变体**（`tool_search_tool_regex_20251119`）使用的是 Python 的 `re.search()` 语法。常见的模式包括用于精确匹配的 `"weather"`，用于灵活匹配的 `"get_.*_data"`，或者是用于不区分大小写搜索的 `"(?i)slack"`。最大查询长度为 200 个字符。

**BM25 变体**（`tool_search_tool_bm25_20251119`）则接受自然语言查询。对于不懂正则表达式的营销团队来说，这要简单得多。这两种变体都会在工具名称、描述、参数名称以及参数描述中进行检索。

| 功能特性 | 正则变体 (Regex) | BM25 变体 |
| :--- | :--- | :--- |
| **查询格式** | Python 正则表达式模式 | 自然语言 |
| **易用性** | 需要掌握正则表达式知识 | 更加直观 |
| **精准度** | 若模式设计良好则精准度高 | 具备语义理解能力 |
| **最大查询长度** | 200 个字符 | 200 个字符 |

### 真实的实现案例

我们的一个客户运行着一个营销自动化工作流，该工作流连接了 Gmail、Slack、HubSpot 以及两个分析平台——这就是我们在《写给营销人员的 Claude Code 指南》中介绍的那种多工具组合。他们最初的实现方式是在前端加载了 50 多个工具定义，在还没开始任何工作之前就消耗了近 15,000 个 Token。这意味着响应速度变慢，并且用于活动分析的上下文空间被严重挤压。

我们测试了“工具搜索”作为替代方案，保留了他们最常用的三个工具（获取活动数据、创建任务、发送通知）为非延迟加载，并将其余所有工具设置为延迟加载。虽然在节省 Token 方面表现出色，但检索的准确率阻止了我们将其推向生产环境。

官方文档涵盖了完整的技术规范。以下是一个简化的结构示例：

```json
{
  "model": "claude-sonnet-4-6-20250929",
  "tools": [
    {
      "type": "tool_search_tool_bm25_20251119",
      "name": "tool_search_tool_bm25"
    },
    {
      "name": "send_email",
      "description": "Send email via Gmail",
      "defer_loading": true,
      "input_schema": {...}
    }
  ]
}
```

### MCP 集成与更宏大的愿景

工具搜索集成了 Anthropic 的**模型上下文协议（MCP）**。MCP 标准化了 AI 代理与外部工具（包括 GA4 和 Figma 等营销工具）之间的连接，我们认为它将成为营销技术栈的“结缔组织”。

借助 `mcp-client-2025-11-20` 测试版请求头，你可以使用 `default_config` 来延迟加载 MCP 工具。在连接多个 MCP 服务器时，这一点尤为重要。未来的愿景是：AI 代理能够通过自然语言在整个营销技术（Martech）栈中自由穿梭，但目前的检索准确率拖了后腿。

### Arcade.dev 的现实检验

Arcade.dev 的团队进行了一项全面的测试，他们加载了 4,027 个工具并运行了 25 个简单直接的工作流。这些并不是极端的边缘案例——它们都是像“给我的同事发一封邮件”或“在 Slack 上发一条消息”这样的日常代理任务。

正则搜索的检索准确率达到了 **56%**（25 个任务中成功 14 个）。BM25 的表现略好，达到了 **64%**（成功 16 个）。但更糟糕的是，常用工具连基本的检索都失败了：“发送邮件”的提示词找不到 `Gmail_SendEmail`，“在 Slack 上发一条消息”错过了 `Slack_SendMessage`，而创建工单的请求也没能搜索出 `Zendesk_CreateTicket`。

> “当‘发送一封邮件’都找不到 `Gmail_SendEmail` 时，这说明还有很多工作要做。”
> —— **Eric Gustin, Arcade.dev**

这还不是关于选择或参数化准确性的问题——这是纯粹的**检索问题**。正确的工具到底有没有出现在搜索结果中？

### 当前的限制与约束

Anthropic 支持你的目录中最多包含 10,000 个工具，每次搜索返回 3 到 5 个相关工具。该功能支持 Claude Sonnet 4.5、Sonnet 4.6、Opus 4.5 和 Opus 4.6——目前不支持 Haiku。它仍处于公开测试阶段，必须使用 `advanced-tool-use-2025-11-20` 请求头。

工具搜索无法与工具使用示例（tool use examples）协同工作，因此依赖少样本提示（few-shot prompting）的团队需要寻找替代方案。正则模式的长度上限为 200 个字符，这意味着你需要非常谨慎地设计模式。常见的错误代码包括：格式错误的正则会返回 `invalid_pattern`，超出长度限制会返回 `pattern_too_long`，触发速率限制会返回 `too_many_requests`。

### 如何实现工具搜索

基于我们的测试，以下是行之有效的做法：

1. **审计**你当前的工具目录和使用模式。
2. **识别**出 3 到 5 个访问最频繁的工具。
3. **保留**这些工具为“非延迟加载”，以确保它们随时可用。
4. **重写**剩余工具的描述，加入语义关键词。
5. **测试**真实营销工作流下的检索准确性。
6. **监控**工具发现的日志，找出未被命中的情况。
7. **迭代**：根据发现规律不断优化工具描述。

在撰写工具描述时，请想一想营销人员在实际中是如何描述任务的。跳过那些技术术语——使用类似“发送营销活动邮件（send campaign emails）”或“从分析工具获取转化数据（fetch conversion data from analytics）”这样的短语。BM25 变体会优待那些清晰、自然的语言描述。

### 这项技术未来的发展方向

这个架构逻辑是非常合理的：延迟加载工具以避免上下文膨胀、即时（just-in-time）发现工具、保持轻量级的交互。其带来的效率提升是实实在在的，并且在规模化应用时会迅速累加。但是，当代理需要可靠地采取现实世界的行动时，60% 的检索准确率显然还未达到生产可用的级别。

> “未来用户交互的阵地将不在网页浏览器中。传统的软件应用程序将主要转变为无头（headless）的后端平台，通过 MCP 等标准向 AI 代理提供数据和功能。”
> —— **Jensen Huang，NVIDIA 总裁兼首席执行官**

对于营销团队来说，这个愿景依然极具吸引力。想象一下，只需输入“向我展示上周产品页面的自然流量”，系统就能自动找到正确的 PostHog 或 GA4 工具，获取数据并格式化结果。在 Growth Method，我们正朝着这个方向努力构建，但我们现在还没到那一步。

### 我现在会怎么做

工具搜索指明了正确的方向。它节省的 Token 数量非常可观，而且自然语言工具发现功能，对于管理着臃肿技术栈的营销团队来说，将是一次阶跃式的变革。

但是，如果在进入选择和参数化阶段之前，就有近一半的工具搜索遭遇失败，你就绝对不能把它放在生产环境中。营销工作流需要“发送活动报告”能够**每一次**都精准找到正确的邮件工具，而不是只有一半的成功率。

目前，请继续在生产环境中使用传统的工具调用。保持对检索准确率改进的关注，并开始着手准备你的工具目录——编写清晰的描述、提炼语义关键词、制定合理的命名规范。当检索变得足够可靠时，那些拥有结构良好目录的团队将能够以最快的速度占据优势。

### 常见问题解答 (FAQ)

**什么是 `advanced-tool-use-2025-11-20` 请求头？**
这是 Anthropic 要求的 API 请求测试版标头，用于在“工具搜索”功能处于公测期间访问该功能。如果没有它，使用 `tool_search_tool_bm25_20251119` 或 `tool_search_tool_regex_20251119` 的请求将会失败。工具搜索支持 Claude Sonnet 4.5、Sonnet 4.6、Opus 4.5 和 Opus 4.6——目前尚不支持 Haiku 模型。

**什么是 `tool_search_tool_bm25_20251119`？**
这是 Anthropic 工具搜索功能的自然语言变体。你不需要编写正则模式，只需使用诸如“发送电子邮件的工具”这类通俗短语进行查询，Claude 会利用 BM25 搜索从你的目录中返回 3 到 5 个相关的工具引用。在 Arcade.dev 进行的 4,000 个工具的测试中，它的检索准确率为 64%——优于正则匹配，但仍未达到生产可用水平。

**什么是 `tool_search_tool_regex_20251119`？**
这是工具搜索的模式匹配变体，使用 Python 的 `re.search()` 语法。像 `"weather"` 或 `"get_.*_data"` 这样的模式可以在工具名称、描述和参数细节中进行搜索，每次查询最多不超过 200 个字符。它需要具备正则表达式知识，并且在独立测试中，其检索准确率（56%）低于 BM25 变体。

**如何启用 Anthropic 的工具搜索功能？**
在你的 API 请求中添加 `advanced-tool-use-2025-11-20` 测试版请求头，在你的 `tools` 数组中包含 `tool_search_tool_bm25_20251119` 或 `tool_search_tool_regex_20251119` 条目，并将你希望按需发现的工具标记为 `defer_loading: true`。同时，请将你最常用的 3 到 5 个工具保持为非延迟加载状态，以确保它们始终可以被立即调用。
